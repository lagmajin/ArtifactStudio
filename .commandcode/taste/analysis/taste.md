The user caught a broad audit sweep that rated components based on .ixx headers alone and demanded re-verification against actual .cppm implementations. Superficial header-level audits that don't check implementation files will be rejected. Confidence: 0.80

This is distinct from feature-gap analysis (what's missing vs AE/Nuke), missing-modules analysis (what doesn't exist at all), and cross-app comparison — it's an inward-facing code quality and completeness audit of an existing subsystem. - When asked to verify that an external library/API is used correctly (e.g. FFmpeg), the user wants the implementation compared against a reference implementation — which the user calls a 「ドナー」(donor) — plus the library's official samples (e.g. FFmpeg's decode_video.c) as ground truth, rather than assessed in isolation. Surface concrete API-misuse bugs (double-free, missing `av_rescale_q` for timestamp rescaling, per-frame re-initialization, uninitialized pointers) and summarize findings with a 🟢/🟡/🔴 severity table plus a prioritized fix list. Confidence: 0.65
- When auditing image/color classes for production-level quality, the user's standards center on: no type proliferation with duplicated responsibilities (12+ coexisting image types for "float RGBA" is a defect; empty stubs like a width/height-only `ImageF32x4` are defects), no dual implementations of the same concept (`FloatRGBA` vs `FloatColor`), color-space metadata carried on the value type itself rather than detached in a separate descriptor, type-safe pixel representation (no raw-byte + string-typed `QString pixelType`), row/scanline access rather than per-pixel copy accessors, and complete operation APIs (rotate/paste/extractChannel/insertChannel/convertTo/applyPixelOp/compare/difference). Good design is recognized too: a fully-specified color-space contract (`SurfaceColorDescriptor` with storage/channelOrder/primaries/transfer/alphaMode/range + `isFullySpecified`/`isCanonical`) and CPU↔GPU cache synchronization (`ImageF32x4RGBAWithCache`). Confidence: 0.65
- When the user suspects an external-library integration (e.g. FFmpeg decoder/encoder) lacks a production-level API, they judge it by the completeness of the *control API* surface — not just whether encode/decode works. Concretely: buffering progress must be real (a stub returning a constant 100% fails), seek must honor its precision/accuracy mode (a `SeekMode` argument that is silently ignored fails), A/V clock synchronization must exist, stream/track selection & switching (multi-audio-language, multi-video) must exist, and HW→software decode fallback must be dynamically controllable. A "can open and decode" state is judged NOT production-level. The user tends to frame this as an unverified hunch (「...ようなきがする」) and expects source-level confirmation rather than dismissal. Confidence: 0.65
- The "production-level API" completeness question (プロフェッショナルでプロダクションなAPIで足りないもの) is not limited to external-library integrations (FFmpeg) — the user applies the same standard to internal domain classes, extending the sweep domain-by-domain (composition, layer, property, then image/color classes). For internal DCC classes, production-level completeness is judged by data-model design quality rather than feature count: live/non-destructive references & links (property pickwhip, driver/driven, master/slave relationships), instance/reference semantics (referencing rather than copying), and efficient data-access patterns (no per-call keyframe-vector copies, no linear scans on sorted keyframes, no JSON-roundtrip clones). Confidence: 0.70
- When auditing the color-management system/pipeline (カラーマネジメント) for production-level quality, the user's standard goes beyond accurate transformation primitives: accurate transfer functions (16 types), gamut matrices (11), real OCIO v2 integration, and 3D LUT support are recognized as production-grade, but the decisive gap is a unified pipeline with a single source of truth — no coexisting ColorManager / ColorScienceManager / OCIOManager systems, no enum/transform duplication (ColorSpace vs Gamut, GammaFunction vs TransferFunction), true ACES RRT delegated to real OCIO rather than a dependency-free approximation, per-source/per-footage input color-space specification, and direct GPU application rather than LUT-bake-only. Confidence: 0.65
