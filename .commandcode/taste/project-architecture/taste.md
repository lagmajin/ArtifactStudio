# project-architecture
- For new functionality in `ArtifactPr`, prefer an internal/centralized event system architecture (the style used in `Artifact/`) rather than ad-hoc Qt signal-slot wiring between widgets. Surface components should publish events to a central bus/service that other layers subscribe to. Confidence: 0.60
- When given a choice between a "faithful/comprehensive" (本格的) port/implementation approach vs a simplified/quick approach, prefer the comprehensive option. The user explicitly chose full tile-based DOF (7-pass Jimenez) over a simplified prepass+main alternative when asked. Confidence: 0.70
- When offered a choice between large feature additions (e.g. multi-stop gradient editor, eyedropper tool) vs a smaller foundational/utility improvement (e.g. adding operators/lerp to a core type like FloatColor), the user may pivot from the feature options to the foundational improvement instead — especially when the foundation has broad cross-cutting impact across the codebase. Value "low cost, wide ripple effect" improvements. The user was offered gradient editor and eyedropper as options 1 and 3, then explicitly chose option 2 (FloatColor operator expansion) when the assistant reframed it as having wide cross-cutting impact at low implementation cost. Confidence: 0.65
- After completing a foundational utility/operator expansion on one core type (e.g. FloatColor), proactively and systematically extend the same improvement to all sibling types in the same domain (e.g. FloatRGBA, Vex2, XYZColor, LabColor) — do not stop at the first class. Furthermore, when the user asks "are there other places that need operators?" (ほかのところで演算子とか必要なのにすくないところある？), go beyond the immediate domain and scan the entire codebase for related types (Animation's DynVec2/3, Graphics' Vec3, etc.) that have similar gaps. The user expects thorough, cross-cutting coverage, not just same-domain consistency. Confidence: 0.75
- After completing a batch of utility/operator expansions in a domain (e.g. color types), the user may proactively initiate a completeness audit by asking "are there other types in this category?" (e.g. "カラークラスってほかにいるかね？"). When this happens, do NOT limit the scan to only types with matching naming conventions (e.g. `*Color`). Instead, also scan the codebase for types that are *used as* colors (e.g. float2/float3/float4 used for RGBA across 40+ files in ImageProcessing/Particle) and report their usage footprint. The user expects an exhaustive inventory of the conceptual domain, not just the obvious naming matches. Confidence: 0.65
- When the user asks "カラーモジュールはほかにやる仕事ってもおうないのか" (or similar questions about remaining work in a module) after completing a batch of improvements, do not limit the scan to types only. Instead, proactively search for broader quality issues in the same domain — especially code duplication (a module re-implementing logic that already exists in another module), import inconsistencies, and consolidation opportunities. The user expects the assistant to identify and flag refactoring/cleanup work beyond just "missing types." Confidence: 0.60
- After completing a full round of improvements in one domain (e.g. color module), the user expects the assistant to proactively offer a systematic cross-module audit of OTHER domains/namespaces too. When the user asks "カラーモジュール以外で足りないものさがして" (look beyond the completed domain for missing features in other modules), respond by scanning each remaining module's types, evaluating their usage footprint, and ranking candidates by cross-cutting impact — not just the immediate sibling types. The user expects cost-benefit tables (usage count, class, deficiency) to guide prioritization of which module to tackle next. Confidence: 0.70
- Prefers consolidating module implementations into a single `.ixx` file (inline/header-only style) over splitting into `.ixx` + `.cppm`. When an audit revealed that `Animation.Dynamics` and `Render.BVH` were already all-inline in `.ixx`, the user's reaction was not "let's separate them into `.cppm`" but rather the reverse instinct — they wanted other thin modules consolidated into `.ixx` too. The assistant's recommendation to separate concrete functions (BVH) into `.cppm` was met with the user proposing the opposite direction. Confidence: 0.55
- When building viewport overlay/display systems (rulers, scale bars, grid labels), prefers a generic reusable framework over a one-off hardcoded feature. The user explicitly asked for "汎用的な" (generic) mechanisms that support multiple simultaneous configurable overlays, arbitrary positions/orientations, and future extensions — not just a single ruler for the immediate ask. Confidence: 0.65
- Strongly prefers shared-memory / zero-copy IPC over socket/pipe-based IPC for performance-critical inter-process data paths (render farm frames, sandbox plugin rendering, GPU texture sharing). The user immediately recognized "共有メモリ不在" from an IPC audit summary as a high-value investment area and requested dedicated milestone planning with D3D11 shared textures, Vulkan external memory, and lock-free ring buffers — valuing throughput/latency reduction over implementation simplicity. Confidence: 0.75
