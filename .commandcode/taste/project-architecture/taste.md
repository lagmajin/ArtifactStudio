# project-architecture
- For new functionality in `ArtifactPr`, prefer an internal/centralized event system architecture (the style used in `Artifact/`) rather than ad-hoc Qt signal-slot wiring between widgets. Surface components should publish events to a central bus/service that other layers subscribe to. Confidence: 0.60
- When given a choice between a "faithful/comprehensive" (本格的) port/implementation approach vs a simplified/quick approach, prefer the comprehensive option. The user explicitly chose full tile-based DOF (7-pass Jimenez) over a simplified prepass+main alternative when asked. Reconfirmed 2026-08-22 (variable expansion): selected 評価時展開 (Houdini-style expansion on every string-property evaluation, keeping frame variables dynamic) over the simpler 確定時展開 (expand once at commit). Reconfirmed again 2026-08-22 (ArtifactPr core-dedup scope question): although the assistant recommended the minimal track (Undo/Redo only), the user picked the maximum scope (Undo＋音声＋デコード全部) and additionally opted for SerializableCommand 化 as future collaboration-sync groundwork — accepting more work now for future-proofing. Confidence: 0.80
- When offered a choice between large feature additions (e.g. multi-stop gradient editor, eyedropper tool) vs a smaller foundational/utility improvement (e.g. adding operators/lerp to a core type like FloatColor), the user may pivot from the feature options to the foundational improvement instead — especially when the foundation has broad cross-cutting impact across the codebase. Value "low cost, wide ripple effect" improvements. The user was offered gradient editor and eyedropper as options 1 and 3, then explicitly chose option 2 (FloatColor operator expansion) when the assistant reframed it as having wide cross-cutting impact at low implementation cost. Confidence: 0.65
- After completing a foundational utility/operator expansion on one core type (e.g. FloatColor), proactively and systematically extend the same improvement to all sibling types in the same domain (e.g. FloatRGBA, Vex2, XYZColor, LabColor) — do not stop at the first class. Furthermore, when the user asks "are there other places that need operators?" (ほかのところで演算子とか必要なのにすくないところある？), go beyond the immediate domain and scan the entire codebase for related types (Animation's DynVec2/3, Graphics' Vec3, etc.) that have similar gaps. The user expects thorough, cross-cutting coverage, not just same-domain consistency. Confidence: 0.75
- After completing a batch of utility/operator expansions in a domain (e.g. color types), the user may proactively initiate a completeness audit by asking "are there other types in this category?" (e.g. "カラークラスってほかにいるかね？"). When this happens, do NOT limit the scan to only types with matching naming conventions (e.g. `*Color`). Instead, also scan the codebase for types that are *used as* colors (e.g. float2/float3/float4 used for RGBA across 40+ files in ImageProcessing/Particle) and report their usage footprint. The user expects an exhaustive inventory of the conceptual domain, not just the obvious naming matches. Confidence: 0.65
- When the user asks "カラーモジュールはほかにやる仕事ってもおうないのか" (or similar questions about remaining work in a module) after completing a batch of improvements, do not limit the scan to types only. Instead, proactively search for broader quality issues in the same domain — especially code duplication (a module re-implementing logic that already exists in another module), import inconsistencies, and consolidation opportunities. The user expects the assistant to identify and flag refactoring/cleanup work beyond just "missing types." Confidence: 0.60
- After completing a full round of improvements in one domain (e.g. color module), the user expects the assistant to proactively offer a systematic cross-module audit of OTHER domains/namespaces too. When the user asks "カラーモジュール以外で足りないものさがして" (look beyond the completed domain for missing features in other modules), respond by scanning each remaining module's types, evaluating their usage footprint, and ranking candidates by cross-cutting impact — not just the immediate sibling types. The user expects cost-benefit tables (usage count, class, deficiency) to guide prioritization of which module to tackle next. Confidence: 0.70
- Prefers consolidating module implementations into a single `.ixx` file (inline/header-only style) over splitting into `.ixx` + `.cppm`. When an audit revealed that `Animation.Dynamics` and `Render.BVH` were already all-inline in `.ixx`, the user's reaction was not "let's separate them into `.cppm`" but rather the reverse instinct — they wanted other thin modules consolidated into `.ixx` too. The assistant's recommendation to separate concrete functions (BVH) into `.cppm` was met with the user proposing the opposite direction. Confidence: 0.55
- When building viewport overlay/display systems (rulers, scale bars, grid labels), prefers a generic reusable framework over a one-off hardcoded feature. The user explicitly asked for "汎用的な" (generic) mechanisms that support multiple simultaneous configurable overlays, arbitrary positions/orientations, and future extensions — not just a single ruler for the immediate ask. Confidence: 0.65
- Strongly prefers shared-memory / zero-copy IPC over socket/pipe-based IPC for performance-critical inter-process data paths (render farm frames, sandbox plugin rendering, GPU texture sharing). The user immediately recognized "共有メモリ不在" from an IPC audit summary as a high-value investment area and requested dedicated milestone planning with D3D11 shared textures, Vulkan external memory, and lock-free ring buffers — valuing throughput/latency reduction over implementation simplicity. Confidence: 0.75
- GPU compute-effect textures follow a canonical-RGBA boundary contract: upload image data normalized via `ArtifactCore::makeGpuImageUploadBuffer(img.surfaceView())` (handles BGRA→RGBA), write HLSL against `px.rgb` with no manual swizzle, and pin the readback descriptor to `SurfaceChannelOrder::RGBA` regardless of the source buffer's order. When adding/fixing a GPU effect, conform to the established reference implementation (GaussianBlur/Blur pattern) instead of inventing a variant. Established 2026-08-21 fixing LiftGammaGain/ColorWheels/Curves R↔B inversion. Confidence: 0.75
- CPU effect kernels must not hardcode channel order (BGRA or RGBA): backing storage order comes from `colorDescriptor().channelOrder` and varies by source (QImage-sourced = BGRA, OIIO-decoded = RGBA). Either branch/index on the descriptor, or wrap RGBA-only processors with swap-in → process → swap-out per row. Confidence: 0.70
- For media frame supply in ArtifactPr (video preview/decode), prefers direct FFmpeg-based decoding over Qt-Multimedia seek-based playback: offered QMediaPlayer+QVideoSink (light, proven MediaThumbnailer pattern, limited realtime) vs FFmpeg direct decode (better for high-framerate playback, heavier/larger scope), the user chose FFmpeg (2026-08-21) — accepting bigger scope for playback capability. Realized via `cv::VideoCapture(cv::CAP_FFMPEG)` reusing the already-PUBLIC-linked OpenCV (vcpkg opencv4 with ffmpeg feature) so no new dependency was introduced. Reconfirmed 2026-08-22 for offline export: SequenceTimelineRenderer decodes via per-source cached `cv::VideoCapture(CAP_FFMPEG)` with a sequential-read fast path, judging the async latest-wins MediaFrameDecoder unsuitable for sequential frame-accurate export. Confidence: 0.60
- When implementing an export/offline path that duplicates interactive behavior, replicate the established reference implementation's exact semantics instead of re-deriving them, and treat preview↔export parity as an acceptance criterion: SequenceTimelineRenderer (2026-08-22) mirrors the ProgramMonitorPanel preview frame assembly (ArtifactPrMainWindow.cppm:682-827) — identical speed/reverse source-frame formula, layer opacity, proxy-substituted `sourceFile` — and transitions stay unrendered in BOTH paths until preview implements them (「トランジションは未合成 — プレビューと同一挙動」). Update 2026-08-22: the preview side now renders transition opacity modulation (Crossfade/Wipe = linear fade, DipToBlack = triangular dip, in ProgramMonitorPanel), so export parity requires porting the same modulation into SequenceTimelineRenderer. Confidence: 0.65
- ArtifactPr EditorEngine edit operations go through the NLE store via the established command pattern: snapshot before (`nleSnapshot()`) → mutate `nleStore_` → snapshot after → `pushUndo(new NLEStateCommand(before, after))` → `rebuildLegacySnapshotFromNLE()` → emit `sequenceChanged`/`projectModified` (2026-08-22 NLE-sync pass converted split/duplicate/paste/lift/rippleDelete/insert/overwrite + marker/transition ops; `NLEProjectStore::removeMarker` was added to Core for the missing delete API). New clip IDs must be the store-returned `ClipId::toString()` — legacy-generated `clip_N` IDs never resolve via `ClipId::fromString` and would permanently strand edits on the legacy-only path. Confidence: 0.70
- Official math/vector types are glm-based, not self-made: module `Math.Vec` (`ArtifactCore/include/Math/Vec.ixx`) exports glm 1.0.3 direct aliases (`vec2/vec3/vec4`, `mat2/3/4`, `quat`, plus `dvec*`/`ivec*`) under namespace `ArtifactCore`. When offered glm-wrap vs consolidating the in-house duplicate Vec3s vs deferring, the user picked glm-wrap (2026-08-22) — rationale: glm is already PUBLIC-linked to ArtifactCore (no CMake change), header-only, battle-tested, SIMD-optimized; direct aliases mean zero conversion cost and full glm API access (no wrapper structs). Conventions: column-major / right-handed / float-default, lowercase glm-style naming. Verified-dead duplicate vector types get deleted (with a fresh repo-wide grep proving import-zero first) to free canonical names — deleting `Graphics/Vector3D.ixx` released the name `ArtifactCore::Vec3`. Confidence: 0.80
- When the user asks to promote (昇格) existing concrete components into a shared higher-level mechanism, they favor consolidating duplicated responsibilities into an intermediate abstraction (e.g. a common container base class) over leaving sibling concrete classes as independent leaves. Evidenced 2026-08-22 when the user asked whether Group Layer / "Mixer Layer" could be promoted upward; the "Mixer Layer" turned out not to exist as a class in code (UI name ≠ class name), and the assistant's analysis converged on introducing an intermediate container abstraction as the realistic form of "promotion." Confidence: 0.5
- Prefers concrete layer classes to stay thin/lightweight: container/hierarchy responsibilities (grouping/bundling child layers) should not accumulate inside a "layer" class. The user described the Group Layer as "too heavy as a layer feature" (レイヤー機能としては重すぎる) because bundling is fundamentally a hierarchy concern that already lives in Composition, not an intrinsic layer responsibility. Favor separating container concerns from layer concerns over letting a layer type grow heavy with them. Confidence: 0.6
