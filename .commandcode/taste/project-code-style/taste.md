# project-code-style
- Do not introduce new QtCSS or `QObject::setStyleSheet(...)` calls in new code; use QPalette, owner-draw, QProxyStyle, or existing theme tokens instead. Confidence: 0.80
- When the stylesheet ban forces owner-draw, take colors from the existing theme API rather than literals: `ArtifactCore::currentDCCTheme()` returning the `DCCTheme` struct (backgroundColor / secondaryBackgroundColor / buttonColor / trackBackgroundColor / borderColor / textColor / textMutedColor / accentColor …), obtained in a widget module via `import Widgets.Utils.CSS;`, then applied through `QPalette` or paint-event overrides following the pattern already used by sibling `Artifact/` widgets. Confirmed acceptable by checking the project rules when planning the expression-editor find bar and line-number gutter (2026-09-26). Confidence: 0.5
- Do not introduce new public `QImage` usage except at IO/compat boundaries; prefer GPU/buffer types. Confidence: 0.80
- Avoid adding new `QObject` signal/slot connections (especially global/centralized event wiring) in new code; reuse existing event paths/services. New public signals/slots need design review. Confidence: 0.80
- Prefers simple callback-based inter-thread communication over Qt signal/slot/emit patterns for worker→main thread dispatch — a single callback dispatched via `QMetaObject::invokeMethod` with `Qt::QueuedConnection`, rather than emit + multi-layer lambda listeners. The user explicitly stated they don't want to use Qt events anymore (「Qtのイベント使いたくない」). This goes beyond "avoid new connections" — the user considers Qt's signal/slot mechanism itself undesirable for the project's architecture. Applied 2026-08-22 in EditorEngine.startExport: worker `std::thread` reports progress via a `std::function` callback bridged with `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`, and completion reuses the pre-existing (never-before-emitted) exportStarted/exportProgress/exportFinished signals instead of declaring new ones. AudioPreviewMixer (2026-08-22) follows the identical shape: level/playback notifications as `std::function` bridged via `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`, plan explicitly 「signal 新規追加なし」. Confidence: 0.90
- When migrating commands onto Core's SerializableCommand base, keep serialization symmetric and self-contained: each command implements `commandType()` as a namespaced constant (e.g. `"nle.moveClip"`), `serialize()` writing only its own members to QJsonObject, and `deserialize()` restoring them + re-setting the QUndoCommand text; reuse existing project-save JSON helpers via forward declarations when they live in the same TU, and verify their namespace/linkage before forward-declaring. Where redo is not idempotent by construction (InsertEdit/OverwriteEdit/LiftEdit create IDs or remove clips), capture the first-redo result in members so repeated redo stays safe under QUndoStack semantics; commands needing pre-computed values expose an explicit compute step (e.g. `computeNewEdges()`) called once before push. Confidence: 0.60
- In the per-frame render path, the dominant cost in this codebase is not the GPU work but unconditional QString construction: summary members (`lastRenderPathSummary_`, `lastCompositionVisibilitySummary_`) filled with long `.arg()` chains, and helper accessors that build a `QStringList` + `join()` each frame. The standing project rule (enforced in `docs/technical/HOT_PATH_RULES.md`: 「診断が無効なときは文字列を構築しない」) means the construction must sit INSIDE the existing diagnostics gate (`captureRenderDiagnostics` / `continuousRenderDiagnosticsEnabled()`) — a guard that merely covers a neighbouring variable while the strings are still built unconditionally is a violation, even though the strings are then discarded. Same family: passing an empty `std::vector<Light>{}` per frame to `setSceneLights` (two further allocations happen inside per layer), calling a getter that returns a `QStringList` per frame and then `id().toString()` inside the per-layer loop (O(selected × layers) string churn), and leaving a profiling scope's `enabled_` default `true` so 30 `ProfileScope`s cost something even with the overlay closed. Two other recurring per-frame offenders: a ticker interval collapsing to 1 ms during playback (the dirty guard limits redraw but not the dispatch), and a repeated identical value written to `std::clog` from a Core `setValue()` rejection path — synchronous I/O, once per frame, worth deduplicating. The landed rate-limiter shape (same session) is an `Impl`-member pair, not a file-scope static, so each instance throttles independently: `m_lastRejectedSignature` composed of name + property type + `QVariant::typeId()` (so a *changed* value re-reports on the very next call rather than being swallowed by the stride) plus `m_consecutiveRejects`, behind a `bool noteRejectedValue(const QString&)` helper and a `static constexpr int kRejectionLogStride = 100`; the first of a run and every Nth thereafter reach the stream, and the log line carries the repeat count. When members are added to a pimpl `Impl`, propagate them in the copy constructor at the same place the existing state (`m_lastError`) is copied. Established 2026-09-26 during the VP / Composition Viewer render audit. Confidence: 0.65
- Do not leave per-frame `qDebug()` logging in playback/render hot paths (e.g. `goToFrame` / timer-tick handlers); when an audit surfaces such logging, treat its removal as an easy inline fix. Confidence: 0.6
- When moving a per-frame diagnostics block behind an existing opt-in gate, the guard is a *behavioral* boundary, not just a cost one — three rules follow. (1) The `else` branch must `clear()` the cached summary members, otherwise a stale string from a frame when diagnostics were last on can be presented as describing the current frame. (2) Before choosing the gate's open/close braces, identify the block's *consumers* and whether they are push- or pull-shaped; a per-frame push into a cache that a pull-side diagnostics dialog (`frameDebugSnapshot()`) only reads on demand will show empty rows when the gate is off — acceptable only because the consumer already filters `isEmpty()`, which must be verified, not assumed. (3) A `qWarning()` that reports a real, already-rate-limited defect (e.g. the per-composition layer-visibility report keyed on a change serial) must be left OUTSIDE the gate even when it happens to sit textually inside the region being gated — silencing a production-relevant warning by default is a behavior change the perf fix did not authorize, and the fix is to place the closing brace above it plus a comment saying why it stays. In all three cases, confirm the gate's brace structure mechanically after the edit (a missing/extra `}` silently produces an orphaned `else` or a compile error much later), and mirror the existing gate's indentation style at that site rather than reformatting the block. Applied 2026-09-26 (VP render controller diagnostics gate). Confidence: 0.6
- When a hot-path fix would make a user-visible diagnostics surface incomplete, do not invent a new opt-in switch for it — wire it to the EXISTING opt-in that already governs that same surface, so the flag-on state is byte-identical to today's behavior and the flag-off state is free. Asked 2026-09-27 as a three-way `ask_user_question` (follow the existing continuous-diagnostics gate / add a dedicated marker file or env var / leave it always on), the user chose the first: gating per-frame `FrameDebugPassRecord` construction behind `ARTIFACT_ENABLE_CONTINUOUS_RENDER_DIAGNOSTICS` (read on the Renderer side, `=1` restores the full content) over a new `ArtifactFrameDebug.enable` marker file, which would have made the FrameDebug view silently empty with no way to tell 「off by design」 from 「broken」. The reporting shape that made the choice legible was naming exactly which rows go blank (the submitter-sourced pass rows) and which remain (the layer-draw rows the controller appends) plus the env var that restores them. Corollary: a member-boolean gate is not enough if the expensive construction sits at the CALL SITE — `recordDebugPass()` was guarded first and that gained nothing, because the 8–20 `QString::number` calls happen in each of the 5 submitters before the call. Confidence: 0.55
- When a rendering backend lacks a native mode (e.g. QPainter has no Subtract blend), do not substitute a visually different approximation (Subtract→Difference); fall back to a neutral mode (SourceOver) with a comment explaining why, keeping the exact implementation on the paths that support it. Confidence: 0.6
- Reader-writer lock (QReadWriteLock) for read-heavy shared state: take QReadLocker on the hot read path and QWriteLocker on the rare write path, so concurrent readers don't block each other (e.g. LocalizationManager.translate() reads under QReadLocker while loadDirectory/reload write under QWriteLocker). Confidence: 0.75
- Re-entrant lock avoidance: an internal/helper method that is only ever called from an outer method already holding the lock must NOT acquire its own lock (would deadlock on re-entry); the caller holds the lock and the callee asserts this assumption in a comment. The same hazard exists across an **event boundary**, and is easy to miss because the two sides look like independent code: if a long-running entry point holds a non-reentrant `std::mutex` for its whole body (`ScriptRuntime::execute` takes a `std::lock_guard` for the entire function, and `updateHostVariables()` runs inside it) and the event bus publishes **synchronously** — so a subscriber's lambda runs inline on the publishing thread — then any event handler that calls a setter taking that same mutex self-deadlocks. Concrete instance 2026-09-26: wiring `setLayerNames()` into a `LayerChangedEvent` / `FrameChangedEvent` handler would have deadlocked on every frame, and the exploration agent flagged it unprompted. Before proposing event-driven push into an existing Core class, read what locks it holds and for how long, and check the bus's delivery mode; the fixes are deferring the write (`post`/queued), or narrowing the lock scope so the per-frame work happens outside it. Related: do NOT refactor a lock/threading contract inside code that has no runtime consumer — the change cannot be validated, so design it together with the first real consumer instead of pre-building it blind. Confidence: 0.7
- A new public class that will hold Diligent/graphics handles should use the project's PImpl rule, and the `.ixx`/`.cppm` split must be *rewritten* in the correct order (`.cppm` first is fine, but the header must be re-read and corrected after any mid-flight signature change). Applied 2026-09-27: the first draft of `GpuProgramMonitor.ixx` was written as an empty stub and then the `.cppm` was written against a PImpl design that the header still described as inline members, producing a real mismatch (`setFrame` signature drift plus a header still exposing `hasFrame()` after the method was deleted). Practical rule: after deleting a public method, grep the header for the name — a `bool hasFrame` member in the Impl was the remaining shadow of the removed accessor. Also note that AGENTS.md's PImpl rule requires an explicitly owned `Impl*` and forbids a `unique_ptr`/`shared_ptr` member in the header. Confidence: 0.6
- A GPU-presenting widget needs three attribute changes together, and the CPU path must be reachable again after a fallback: `WA_NativeWindow`, `WA_DontCreateNativeAncestors`, `WA_PaintOnScreen` plus `WA_NoSystemBackground` and `setAutoFillBackground(false)` when GPU is on; the reverse (restoring the palette and auto-fill) belongs in the fallback path, not left implicit. Corollary: when a widget gains a GPU mode, every derived measurement that previously read the CPU-side artifact (here `cachedImage_`, a QImage that is deliberately not created on the GPU path) must be redirected to the source of truth instead — `fitScale()` and `wheelEvent` were both reading the now-empty `cachedImage_`, which would have silently pinned zoom to 1.0. Factor the shared decision into one accessor (`sourceSize()`) so the two paths cannot drift. Confidence: 0.55

- After editing .cppm/.ixx files, verify brace (`{`/`}`) and parenthesis (`(`/`)`) balance by counting both deltas (each must be 0) before running audits or builds. Do this on a view with string-literal contents stripped first — naive counting produces false positives when string literals contain delimiter characters (e.g. the `1)`/`2)`/`3)` numbering inside a translated message reported a phantom `paren -3` in `ArtifactTestMenu.cppm`, 2026-09-18). Keep a string-aware checker (regex-replacing `"..."` with `""` before counting) as the canonical balance tool. The same check applies to build files edited in the pass — a `CMakeLists.txt` paren count plus a count of the new flag/keyword (`s.count('ARTIFACT_ENABLE_PYRO')` should equal the number of intended definition sites) is the cheap desk-check to run when a real `cmake` configure is off-limits under the no-build rule. Confidence: 0.70
- Evolve widely-used APIs backward-compatibly: extend signatures with optional trailing parameters with defaults (e.g. `std::optional<int> layerIndex = std::nullopt` on `AbstractProperty::evaluateValue`) so existing call sites compile untouched, rather than changing signatures or editing callers. Expose compatibility names as registered aliases to existing implementations (`seedRandom` → `randomSeeded`) instead of duplicating code; prefer pure additions (new registered builtins, no parser/evaluator-core changes) when a minimal-impact pass is requested. Confidence: 0.70
- New shortcut IDs ship with **no default key binding** (unassigned / empty `QKeySequence`), leaving assignment to the user — the user rejected the assistant-recommended default (`Ctrl+Alt+T`) in favor of 未割当て. Registering one requires the full chain (`.ixx` enum entry before `Count` + `Count` increment, `shortcutDisplayName`, the display-name table, `allShortcutIds()`), plus an explicit context mapping in the settings dialog's `shortcutContext()`, whose range-based fallback otherwise files new IDs under `Workspace.Timeline`; `ShortcutBindings` stays the single source of truth (no hardcoded keys in the widget). Not an absolute rule: a later, approved plan shipped `ShortcutId::ViewToggleMagnifier` with the default `Alt+Z` (2026-09-21) after verifying the key was unclaimed — treat 未割当て as the safe default when the candidate key is uncertain, and a conflict-free default as acceptable when the approved plan names it. A batch of *conventional* editor keys is the case where defaults are appropriate: for the expression editor the 11 new IDs shipped with `Tab` / `Ctrl+F` / `Ctrl+H` / `F3` / `Shift+F3` / `Esc` / `Ctrl+=` / `Ctrl+-` / `Ctrl+0` / `Alt+L` / `Alt+Z`, each justified in a code comment by what it shadows. Cross-context key reuse is legal (`Ctrl+=`/`Ctrl+-`/`Ctrl+0` are also Timeline zoom) because bindings only conflict *within* one context and the editor consumes them on its own focused control; a key like `Esc` is acceptable when it is consumed only while that surface's own UI (the find bar) is open. When adding a batch, append the new IDs after the existing ones and bump `Count` so persisted ordinals stay stable, and keep the `allShortcutIds()` append order identical to the enum order because the settings table looks rows up by ordinal. Confidence: 0.6
- A shortcut registered in `ShortcutBindings` is resolved only by the surface that owns the behavior (e.g. the composition viewport resolves `ShortcutId::ViewToggleMagnifier` in its `keyPressEvent` via `ShortcutBindings::matches(event, id)`), and the same key must NOT also be attached to the corresponding menu `QAction` via `setShortcut()` — doing both lets Qt's shortcut machinery consume the key and creates double ownership. Menu entries may display/look up the ID but do not bind the key. Applied 2026-09-21 while adding the accessibility magnifier (the plan's initial `setShortcut` on the View-menu action was removed before delivery). Confidence: 0.5
- After editing files in this repo, verify you have not silently flipped LF→CRLF. The reliable procedure is: count CR-LF byte pairs in the working-tree file, compare against the committed blob (`git show HEAD:<path>`), and normalize only the files your edit actually broke. PowerShell: `[IO.File]::ReadAllText($p)` → `-replace "\`r\`n","\`n"` → `[IO.File]::WriteAllText($p, $t, (New-Object Text.UTF8Encoding($false)))` — the explicit UTF8Encoding($false) avoids injecting a BOM. Two traps: normalizing a file that was ALREADY CRLF in HEAD produces an enormous spurious diff, and a file that was cleanly reverted can still show as modified from a stale stat-cache entry, so confirm with `git diff --stat HEAD -- <path>` before concluding a revert failed. Re-check `git diff --stat` after normalizing to confirm the change stayed minimal. Applied 2026-09-26 across five files (ViewerHelperShaders.ixx, two .ixx files, en.json, ja.json) after edits silently rewrote the whole file with CRLF. Confidence: 0.7
- Before ending a turn, read the full `git diff` hunk by hunk and revert anything that is not part of the intended change: whitespace-only edits on adjacent lines, a blank line swallowed by an anchor-based replace, dead parameters (`Q_UNUSED(format)`), and a local that shadows a member. Anchor-based `edit_file` replacements frequently trim or duplicate the neighbouring line, so a per-file `git diff -- <path>` review is the reliable catch. The specific sub-case worth naming, seen 2026-09-27: an edit that anchors on a line carrying an *escaped* non-ASCII character and inserts a block above it came back with the escape rewritten to the literal character (`QStringLiteral("More Viewport Actions\u2026")` → `"More Viewport Actions…"`). It compiles and renders identically, so nothing but the diff catches it — which is why the escape form must be restored rather than 「harmonized」 when the change was not requested. Same class: a value written as an escape in the original (`"Overlap Pin"` labels vs `\uXXXX` in neighbours) is not an invitation to normalize. If an implementation approach is abandoned mid-task, revert the file completely and verify the diff is empty rather than leaving partial scaffolding behind. Applied 2026-09-26 while implementing the viewport exposure feature: three such unintended edits were caught and reverted in `ArtifactIRenderer.cppm`, `ArtifactViewMenu.cppm`, and `ArtifactCompositionRenderController.cppm`, and an abandoned `ApplicationSettingDialog` UI was confirmed to have zero diff. Confidence: 0.65
- Before committing, check the *index* line endings rather than the working tree: `git ls-files --cached --eol <paths>` — `i/lf` means the blob that will be committed is LF regardless of what the checkout shows, so a `w/crlf` / `w/mixed` column entry is a benign checkout-state artifact under a `.gitattributes` carrying `eol=lf` (with `core.autocrlf=false`) and needs no re-normalization. Cross-check with `git diff --numstat -- <paths>`: a small `24 23` proves the CRLF checkout state did not turn the commit into a whole-file rewrite (git compares the LF index against the normalized worktree), whereas insert/delete counts in the thousands mean a real EOL problem. Applied 2026-09-26 while preparing the color-effects commits. Confidence: 0.6

Operational rule: an `edit_file` fix aimed at a corrupted span can fail to match because the on-disk bytes differ from the string being searched, and the corruption is often *invisible* in the read-back — when two successive targeted edits fail to clean a span, stop patching and rewrite the whole file with `write_file`, then re-grep for markers and re-read the file end to end before continuing. Two lessons: a replacement can *compound* the corruption instead of converging on a fix, so after two failed attempts stop hand-tuning the string and route the clean text through a file; and never trust the tool's success return — the remaining error was only caught because the patch script `print`ed the neighbouring lines back, so always echo the patched region before declaring a file clean. - Self-review of freshly written code should sweep four categories beyond compile blockers, and fix them in the same pass: (1) unused declarations left behind — an anonymous-namespace constant duplicating one owned elsewhere, an `import` no longer referenced, a setter with zero callers; (2) redundant one-line wrappers that add nothing around an existing call (`bool documentFind(...) { return edit->find(...); }`, a getter that returns a literal color); (3) one effect implemented along two paths — the current-line band was painted in `paintEvent` *and* as a `FullWidthSelection` ExtraSelection, double-applying the alpha; keep one drawing path per effect and say in a comment why the surviving one is correct; (4) handlers orphaned by a later change (an Escape branch for a strip that the new find bar's own Escape now supersedes); (5) a variable whose NAME asserts an outcome it does not compute — a `bool comparisonSaved` derived from `json.toStdString().size() > 0` while the report is only `fprintf`ed to stderr, which is a report that does not exist wearing a success flag's name; the fix is the real write (`QFile::open` + `write`) or an honestly named `reportBuilt`. Applied 2026-09-26; the fifth category caught 2026-09-27 in the dual-run harness's own first draft, before delivery.
