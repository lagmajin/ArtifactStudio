- The gate fires on a boundary that SYNTAX improvement crosses, and 「the request was explicitly about ergonomics」 is what makes the parent-only workaround lose. Applied 2026-10-06 (script-API usability): three of the four accepted capability groups shipped as `host.registerFunction` calls inside `ArtifactAbstractComposition.cppm` with ZERO Core edits — the announced framing being 「Host関数として実装する形にします（Core を編集せず Artifact側だけで拡張できます）」 — but the `this.xxx` shorthand could not be, because the requested form was syntactic. The fork offered (a) `getSelfProperty` / `setSelfProperty` host functions with the parser untouched, (b) implementing `this` in the evaluator's `FieldAccess` / `Assign` paths（「Core 変更大 (Recommended)」）, (c) dropping `this` from scope entirely; the user took (b). This is the same rule the `Composition.Registry` entry recorded — **the per-repo approval gate is not a reason to ship a workaround when the capability is a LANGUAGE-level one** — but the axis is new. There, the crossing was forced by a module CYCLE, so no parent-side equivalent existed at all; here a parent-side equivalent existed, was fully implemented in the same pass, and was rejected because it left the USER-VISIBLE SCRIPT TEXT unchanged, which was the entire point of the request. So the gate question must price a workaround in the unit the user actually cares about — for an ergonomics request that is 「what the script still looks like」, not 「how many files change」. Two riders. (1) **The option's own cost estimate was wrong, and the cheap instrument is reading the mechanism that would have to change**: the preview said 「Core 変更量が多い」 on the reasoning that a new keyword requires a parser, but reading the parser showed `this` was already a RESERVED variable and `this.X = v` already parsed as a `Decl` carrying `fieldAssign = true` / `declName = "this"` / `assignField = "X"` — so the landed change was three evaluator sites and NO parser edit. This is the recorded 「an option's description is a mechanism claim」 applied to its COST axis, and it is worth deriving before the menu goes up rather than letting the delivery contradict the option the user chose. (2) The reuse the fix rested on is the in-file precedent worth naming: inside a method `activeThis_` IS the script instance, so the change is a FALLBACK for the `!activeThis_` case only — and BOTH halves need the same guard, because the `Variable` case errors out before `FieldAccess` ever sees the access (the first draft made the `FieldAccess` fix first and only then discovered the `Variable` branch had to stop erroring too).
- `ArtifactCore` is a CHILD repo under the same boundary rule as `ArtifactWidgets` / `libs/…` / `third_party/*`, even though the standing rule's wording names only those three — so a fix that must land in Core is gated on an explicit approval, not assumed. Applied 2026-09-30 while neutralizing the layer-bus `pan`/`volume`; the user approved and it shipped. Reconfirmed a second time 2026-10-02 on a VST/CLAP consistency pass: the user's 「じゃあ全部修正を」 plainly named items in `ArtifactCore` (`CLAPHost.cppm` search paths, the dead `include/VST/` stubs), the parent-side items were completed first, and the Core items still went back behind one multi-select gate. That pass also surfaced a form the gate is unavoidable for: one report item required an interface to be IMPLEMENTED by a child-repo type, so no parent-only edit could have closed it at all — and the option's preview said so explicitly rather than promising a parent-side fix. When an option's preview must confess that the fix crosses the boundary, that is the option being honest, not a weak option. Two reporting rules that came with it. (1) The gate is per-repo, not per-pass — completing every parent-repo site and then asking once for the whole Core change is the efficient shape, and the approval does not retroactively authorize other Core edits later in the same session. (2) The approval question should state which behavior each option leaves in place (「評価パスが毎ブロック 0dB/中央に強制するので保存済み pan は評価時に上書きされるが無害」 is what makes the do-nothing option a real choice rather than a non-option). **Refined 2026-10-01: the gate fires even when the CORE change is what the user already asked for in plain language.** The user replied 「これらをすすめてほしい」 to a deferred list whose two items were both named as living in `Mesh.cppm` / `MeshRenderer.cppm` — i.e. the authorization was explicit and specific, and the pass still paused to read the exact code and then put ONE `ask_user_question` in front of it rather than proceeding. So the rule is not 「ask when the user did not say so」 but 「the per-repo approval is a separate gate from the task authorization, and reading the code first makes the request concrete」 — the value of the read-before-asking is that the option descriptions can then carry the CONSTRAINT you discovered (which buffers are rewritten per frame and which are invariant; whether the index buffer may be coalesced with them; which sub-items are independent of each other), which is what makes the multi-select worth answering. The shape that worked: one option per sub-item rather than a blanket 「Core 変更してよいか」, each description naming the file:line and the reason the sub-item is separable, plus a 「両方」 and a 「Core に触れず」 escape — and each option ALSO carrying its own limitation honestly (「アニメーション中は revision が毎フレーム増えるためこのキャッシュは効かない」), because the standing rule that a caveat in an option must not pre-empt approval runs both ways: the caveat has to be visible BEFORE the choice, not discovered in the report. - Do not modify, commit, or push the `ArtifactWidgets`, `libs/...`, or `third_party/*` submodules unless the user explicitly asks; treat them as read-only/external. New UI widgets are first placed under `Artifact/` and only promoted to `ArtifactWidgets/` later. When a feature looks like it needs submodule work, verify the *consumer-side* API before assuming so — if the public interface takes a whole-frame object (e.g. `updateFrame(const QImage&)`) and the caller already holds the full frame locally, a rect-limited feature (ROI) is achievable with a single `frame.copy(x,y,w,h)` at the call site and the submodule boundary is never crossed (2026-09-26, scope ROI). Consequently prefer a CPU-side parent-repo path as stage 1 and defer any GPU/submodule version to a later stage gated on measurement, instead of blocking on a fork/patch decision up front. The sequence that handles it is worth reusing verbatim. (2) PROVE the child repo is back to its prior state with `git -C <child> diff --stat`, and read the OUTPUT rather than the silence: the run showed `MeshRenderer.cppm` absent but `PluginRegistry` still listed, and the honest reading was 「`MeshRenderer.cppm` の差分は残っていません（`PluginRegistry` の差分は本作业の前から存在する Sessions 级のもTolerance）」 — i.e. an unrelated pre-existing child diff must be named as NOT mine, exactly as the standing pre-existing-work rule requires, so the user does not later blame this pass for it. The compensation must carry a comment naming the assumption it is compensating for and the Core file:line that could otherwise hold it, so a future pass knows the debt is real rather than closed. Reporting 「ArtifactCore の変更はゼロ」 at the top of the summary is then a fact, not a hedge. Confidence: 0.55

- A constraint discovered in the CHILD repo's SIGNATURE is a PLACEMENT fork, and the discriminator between taking the child-repo option and a parent-only re-derivation is whether the capability is a PURE FUNCTION the app can call itself — not which route is cheaper. Established 2026-10-06 (ArtifactScript binding): `ArtifactScriptHotReload::definitionFor(path)` returns a `const&` to a move-only `ArtifactScriptDefinition`, so the Layer could not take ownership without a new `takeDefinition` in `ArtifactCore`; the fork was (a) add `takeDefinition` to Core (要承認), (b) have the Layer read the file and run `ArtifactScriptParser{}.parse(source)` itself (Core無変更・推奨), (c) re-read and re-parse on every evaluation (ホットパス違反) — and the user took (b), the parent-only option. That is the OPPOSITE pick from the recorded soft-body case, where only `PhysicsSystem`'s own solver registry could step the body and the user took the Core-naming option over a one-line flag flip. **Third case, 2026-10-06, and the user took the Core option — the rule now has two losing conditions, not one:** the child-side defect was in a LOOKUP the parent's own call path lands in (`invokeHook` / `hasHook` scanning only `definition_.rootClass.methods`, so a derived class's `OnUpdate` failed with 「unknown method」 while the body it dispatched to already walked the chain via the unused `findMethodInChain`). The parent-side alternative the fork offered was to copy the derived hooks into `rootClass.methods` before every evaluation, and it was honest about its cost (a per-evaluation copy plus 「Core のバグは残る」) — the Core option won because the cure was to reuse a helper already sitting unused in the child. So the reconciling rule reads: **the parent wins when the work is a pure function the app can call itself without leaking reach into a child registry; the child wins both when the work is dispatch THROUGH a registry the child owns AND when the broken code is the exact lookup the parent's call path enters.** The gate question's option descriptions must therefore price the parent-side workaround's RECURRING cost per evaluation, not merely say 「Core 無変更」 — the approval is much more likely to be granted against a named recurring cost than against a cleanliness claim, and the whole parent-side half of that pass (binding UI, host API wiring, hot reload) was completed before the gate fired, which is the already-recorded per-repo sequencing. Confidence: 0.5 So the reconciling rule is: **parent-only and architecturally-correct are separate axes, and the boundary does not by itself make the parent-only option the cheap one — the parent wins when the work is a self-contained function the app can call without leaking its reach into the child's registries, and loses when the work is dispatch THROUGH a registry the child owns.** Three reporting obligations. (1) The constraint must be read out of the child's HEADER before the fork, because nothing in the parent fails until a build the standing rule forbids — a move-only return type is invisible to grep, so 「we cannot take ownership」 is a claim with no symptom until much later. (2) The parent-only option's preview must name what the child-repo option would have bought (here: the already-implemented `ArtifactScriptHotReload` mtime polling that the re-parse route leaves unused), so 「ArtifactCore の変更はゼロ」 reads as a fact with a stated price rather than as a silent regression. (3) The delivery's 未確認 block still lists the child's existing-but-unused capability by name (「hot reload 未接続。`ArtifactScriptHotReload` は Core に実装済みだが、今回の方式では使っていません」), because a later session reading only the file would otherwise re-derive it from scratch. The same pass's confirmed preference for the ARCHITECTURALLY-correct option over the parent's recommendation appeared again in the question text itself, where the recommended option was labelled 「Core変更・要承認」 and the assistant had put the parent-only route second. Confidence: 0.5
**Reconfirmed the next day on the same ArtifactScript thread, and it pins down a case the three recorded ones did not cover: when the ONLY architecturally-correct option requires a NEW MODULE in the child repo, the user picks it — the per-repo gate is not a reason to prefer a workaround.** Applied 2026-10-06 (cross-composition reference): the manager already imported the composition module, so the fork was (a) add a name-lookup API to `ArtifactProjectService` — still a cycle, since Service→Composition already exists and Composition→Service would close it; (b) an `import Artifact.Project.Manager` weak reference from the composition, which the option preview itself flagged as a compile error because MSVC rejects module cycles outright (a weak POINTER does not help — the cycle is in the import graph, not in the object graph); (c) a dependency-zero `Composition.Registry` in `ArtifactCore` holding `void*`, with compositions self-registering. (c) was marked 推奨 and taken. Two things generalize. (1) **The gate question must distinguish 「a change to a child type's BEHAVIOUR」 (the recorded cases) from 「a new child MODULE that exists only so the dependency arrow can point the other way」** — the latter has no parent-side equivalent at all, since the whole point is that the parent cannot host it, so framing it as a cheap parent workaround is not offering a real choice. (2) **An option preview that says 「MSVC はモジュール循環を許容しない → コンパイルエラー」 is doing the strongest work in the question**: it converts a soft architectural preference into a hard toolchain fact, which is what makes the crossing-repo option the obvious pick rather than a concession. Corollary for the report: a new child module is a whole-project re-scan factor under AGENTS.md, so it must be flagged as a deliberate deviation from 「prefer appending to an existing file」 with the reason (a cycle cannot be appended away) — the same 「deviation is correct and must be named」 shape already recorded for the Text.ShapingBackend consolidation.
