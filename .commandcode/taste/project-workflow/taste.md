# project-workflow
- The Reactive Event system (ReactiveEvents, ReactiveEngine, ArtifactReactionExecutor) is off-limits for modifications, improvements, or implementation proposals unless the user explicitly requests work on it. Do not touch it or suggest enhancements. Confidence: 0.85

- For developer branch naming in the parent-child repos, use a generic suffix (e.g. `codex/YYYY-MM-DD-dev` or just `codex/YYYY-MM-DD`) rather than a feature-specific name like `codex/YYYY-MM-DD-<feature>`. The branch should reflect ongoing development, not a specific milestone or feature set. If the user rejects a feature-specific name and picks a date-only alternative, use the date-only format. Confidence: 0.80
- Do not run build, tests, or formatting commands for the ArtifactStudio project unless the user explicitly requests it. Confidence: 0.90
- When the user explicitly says to skip runtime validation because it's heavy (重いのでスキップ), respect that directive. Do not re-run or insist on validation. Confidence: 0.85
- Do not commit or push to the parent/child git repos (Artifact/, ArtifactCore/, ArtifactWidgets/) unless the user explicitly asks; just stop at the file-edit step. Confidence: 0.85
- Before creating a new feature/widget/file, verify by exploration that an equivalent implementation does not already exist (under any name/alias) in the workspace; only proceed if the check is explicit. Confidence: 0.60
- When `git status` shows modifications to files outside the current task scope, treat them as the user's in-progress work; run `git diff` to understand intent but do NOT revert, edit, or commit those changes. Only touch files directly required by the current task. Confidence: 0.85
- File extensions and naming conventions matter: if files have inconsistent/inappropriate extensions (e.g. a `.cppm` file that isn't actually a C++ module, or mismatched naming patterns), consider them worth fixing gradually. The user finds such inconsistencies 「気持ち悪い」(gross/annoying) and prefers incremental cleanup. Confidence: 0.70
- The project is on Windows; `find` and `grep` are NOT available in shell. Use `findstr /S /N /C:"pattern" path` for text search, `read_directory` for directory listing, and `glob` for file pattern matching. Confidence: 0.75
- Use a dedicated git worktree for AI-assisted work sessions (e.g. `X:\dev\commandcode-wt-YYYY-MM-DD` on branch `dev/commandcode-YYYY-MM-DD`) instead of working directly on `main`. The main repo should be left untouched. Confidence: 0.80
- `write_file`/`edit_file` are restricted to the main repo workspace (`X:\dev\artifactstudio`) and reject paths inside the worktree. When asked to save to a worktree path, ask the user to confirm placing it in the main repo's `docs/reports/` (or similar) rather than retrying with shell heredoc. Confidence: 0.80
- For "large / 大量" utility/API proposals targeting `ArtifactCore` (e.g. string helpers, random/noise helpers), the user's typical workflow is: explore existing code first (depth: medium), then write a structured proposal markdown to `docs/planned/STRING_HELPER_PROPOSAL_YYYY-MM-DD.md` (or similar) with sections for current-state inventory, module groups labeled A-J, ~100 function signatures, priority levels (★★★/★★/★/○), test policy, and related files. Stay in proposal mode unless user explicitly asks to start implementation. Confidence: 0.60
- When the user requests milestone documents (マイルストーン), write them as detailed, thorough files with full phase planning, existing-asset analysis, design pillars, invariants/guardrails, and relationships to existing milestones. Save directly to disk. Do not produce short summaries when the user asks for 詳細 / しっかり / 詳細に. The user prefers comprehensive, time-invested milestone documents. Confidence: 0.80
- For analysis/investigation reports (ソース調査 / パフォーマンス分析 / 機能ギャップ調査), write thorough markdown reports to `docs/analysis/REPORT_*_YYYY-MM-DD.md` with full methodology, structured tables of findings (OK/PART/MISS counts), severity classification (重大度 S/A/B), prioritized fix recommendations, and connections to existing milestones. Follow the same comprehensive-investment pattern as milestone docs. Clean up temporary scan scripts (`_*.py`) after the report is written. Confidence: 0.70
- For empty/placeholder stub implementations (e.g. CSharpScriptEngine skeleton), do NOT propose deletion. Implement them instead when work on that area is requested. The user explicitly rejected a deletion suggestion and asked for implementation. Confidence: 0.70
- The user proactively calls out stub/placeholder implementations of core infrastructure as unacceptable (「いただけない」) — e.g. a TBB-based `Parallel::For` that was supposed to use TBB but was left as a stub. When the user discovers core infrastructure stubs (especially ones that exist specifically to wrap a library like TBB), they expect them to be implemented properly, not tolerated as known gaps. Confidence: 0.65
- When implementation scope exceeds the session budget (e.g. requires full render engine, audio engine, etc.), explicitly propose a separate milestone ID (M-PR-XXX-N), implement a minimum viable alternative for the current session, and document the deferred work in the final summary. Do not silently skip features that the user asked for; surface the deferral. Confidence: 0.75
- When creating a new development branch in the parent repo (e.g. `codex/YYYY-MM-DD`), also create branches with the same name in all submodules (Artifact, ArtifactCore, ArtifactWidgets) so that simultaneous development can proceed under a unified branch naming scheme. Confidence: 0.60
- When the user responds to brainstorming/proposals with "アイデア集としてメモしといて" (keep it as an ideas collection), preserve the ideas as an informal ideas document — lighter than a milestone doc, labeled as 発想メモ. Do not convert them into formal milestones unless the user explicitly asks. The `docs/shared/` directory can be used for this purpose. Confidence: 0.65
- The user expects the assistant to be able to read, understand, and continue executing milestones and memos created by other AI assistants (「ほかのAIが最近作ったマイルストーンやメモ実行できそうか？」). The assistant should treat docs from other AIs as actionable work, not dismiss them as foreign. Confidence: 0.65
- When the user says "ファイルにメモして" (save it to a file) after investigation/debugging findings are presented in chat, persist them as a structured markdown memo. Use `docs/memo/<TOPIC>_<DESCRIPTOR>_YYYY-MM-DD.md` naming — `BUG_*` for bugs, descriptive topic + descriptor for feature-gap/audit memos (e.g. `OCIO_MISSING_FEATURES`). These are focused single-topic memos, distinct from comprehensive `docs/analysis/REPORT_*` reports. Confidence: 0.70
- When the user asks for a comprehensive enumeration of expected behaviors for a UI feature ("できるべき動作をすべて列挙"), create a thorough feature requirements spec document saved to `docs/spec/SPEC_<NAME>_YYYY-MM-DD.md`. Structure it with: visual behavior, each interaction type (drag modes, modifier keys, snapping), integration with sibling systems, and an implementation-status checklist (done/gaps). This is a distinct document category from `docs/analysis/` (investigation reports), `docs/memo/` (bug memos), `docs/planned/` (proposals), and `docs/shared/` (idea collections). Confidence: 0.70
- The user distinguishes between a task list/spec ("what needs to be done") and an implementation guide / 実装手順書 ("how to implement it step by step"). When the user asks for 実装手順書 as a follow-up to a task list, create a separate companion document (`docs/spec/SPEC_<SYSTEM>_IMPLEMENTATION_GUIDE_YYYY-MM-DD.md`) with: numbered phases, each step specifying exact file paths and insertion points, ready-to-paste code snippets, inline verification checkpoints, a final verification checklist, and an estimated-effort table. Defer complex/invasive phases explicitly with a rationale (e.g., "後回し推奨" for timeline integration). Confidence: 0.65

The user accepted this format without objection when the assistant delivered it after the user's "モジュールの順番に調べて" request. Confidence: 0.65

The user asked "順番に見ていってくれる？" (can you go through them one by one?) rather than requesting a full report. Confidence: 0.65

The user explicitly said "新規ファイル作成はなしで" (no new file creation) — add new classes/structs/functions to existing `.ixx`/`.cppm` files rather than creating separate files for each new module. Only create new files when the existing ones would become unmanageably large or when a truly independent subsystem warrants it. Confidence: 0.85

Deep per-file code analysis is not required for high-level structural overviews; save that depth for focused investigations. Confidence: 0.55
