Rules. (1) **The 理由 column of a deferred table is a HYPOTHESIS, and quoting it verbatim as an option description sends the user pricing on a number the source may contradict** — the correction belongs in the option preview, because that string is the only thing the user reads before selecting, and this is the 「an option's description is a mechanism claim」 rule applied to its COST axis. (2) Re-derivation is cheap (four reads) and the payoff is structural: the reclassified item stops competing with the items that genuinely need new machinery, so the menu's ordering becomes meaningful rather than a guess. (3) **The pass must amend the prior report's own table in the same turn** — flip the state column to 修正済み, delete the row from the 未着手 list, rewrite the 修正推奨 row with the real file count, and refresh the 更新内容 header line — because that table is exactly what the user reads to choose the next item, and a stale 「設計変更が必要」 will send the following turn chasing a constraint that does not exist. (4) The evidence for 「wiring only」 is a NAMED existing implementation the user can check (`FFmpegEncoder に既に tmcd 埋込がある`), never the adjective. Related to — but distinct from — the recorded 「(Recommended) does not license shipping garbled option text」 and the 「option cost estimate was wrong」 cases: those are about a wrong claim surviving into the menu, this one is about the PREVIOUS turn's report being wrong and the menu being where it gets caught. - A repeated-shape `edit_file` that rewrites a whole `if`/`else` block across SIBLING functions has two mechanical failure modes that only a read-back of the SURROUNDING lines catches, and both appeared in one pass 2026-10-05 while applying the same refactor to three copies of the same branch. The recovery that converged: re-read the exact offset range, then grep the ORIGINAL call site's own argument (`FramePosition(frame)` vs `FramePosition(frameNumber)`) to obtain the right expression rather than inventing one, re-emit BOTH the restored declaration and the corrected call, and finally grep the file for the invented token plus the new lambda's name to prove nothing else was half-applied. Generalize: (a) before re-emitting a rewritten block, enumerate what lies IMMEDIATELY AFTER the replaced region in the original and check each name still appears; (b) when an API needs a value you do not have in scope, grep the sibling call site for the argument — a name that names nothing is invisible without a build, and the standing no-build rule makes the grep the only instrument; (c) for a N-sibling sweep, the third copy is where the inattention lands, so budget a per-site read-back rather than assuming the first two proved the pattern. - **A markdown report TABLE must be rewritten ROW-WHOLE from a tuple, never patched cell-by-cell by index or by `split('|')` — because the cell count is the thing every repair script gets wrong, and each wrong guess silently eats a neighbouring column.** Seen 2026-10-07 when 14 audit rows had to be flipped to 修正済み with file:line evidence. Four rounds, each a different corruption of the same table. (1) The first script assigned `cells[3] = status; cells[4] = ' ' + evidence + ' |'` — appending a `|` inside the cell it was writing, so the row came out with an extra column and the next script found `||` markers. (2) The collapse script assumed exactly 7 cells, re-derived the missing axis column from a hardcoded per-item dict, and produced rows that were still wrong. (3) The next attempt hit 8 cells and gave up on parsing. (4) What converged was abandoning the parse entirely: a `{lineno: (id, desc, axis, status, evidence)}` dict emitting `'| ' + ' | '.join(fields) + ' |'`, with a `print` of the resulting line per row, plus a separate dict for the two non-default statuses. Three rules. (a) **The evidence cell must never contain a literal `|`** — the Japanese form of a file list is ` / `-separated backticked paths, and a pipe inside a cell is what the splitter cannot see. (b) **Print the emitted row inside the same script that writes it**, so the verification is the writer's own output rather than a later `read_file` of a file the tool already reported as saved. (c) **The axis/severity column is data, not a guess** — re-deriving it from the item id is how a row silently lands in the wrong table; carry it in the tuple. The whole class is the 「change the INSTRUMENT when the result disagrees with the surrounding evidence」 rule applied to text surgery: three repair rounds on the same rows is the signal, not the iteration count. Confidence: 0.55

- A reported bug whose defective code is UNREACHABLE converts 「fix it」 from a straight edit into a SCOPE FORK, and the fork's honest default is the option that changes no runtime behaviour. Applied 2026-10-05 (an HLSL kernel whose temporal derivative subtracted the same pixel from itself): the assistant's own prior report had flagged it as 「特に違反寄り」, but the reachability check run BEFORE the edit — grepping `supportsGPU()` and then the abstract base's gate (`mode == ComputeMode::GPU && supportsGPU()`, `ArtifactAbstractEffect.cppm:700,703`) — showed the GPU impl is never entered, so no fix could change what a user sees. So 「proven dead」 is not by itself a deletion licence in this repo: the decision axis is whether the dead code still documents or derives something the SURVIVING path depends on (this impl is the reference for the premultiplied linear Gaussian the resident node no longer spells out), and when it does, the deliverable is a comment that (a) names the exact mechanism that makes it unreachable, (b) enumerates the conditions that keep it that way, (c) states the standing rule it would violate if it ever ran, and (d) points the reader at where new work belongs instead. That is a THIRD axis alongside cost and architecture, and it can outrank the assistant's own `(Recommended)` deletion — so the recommended option must be the one the assistant would ship, and the doc-instead-of-delete option has to be present and honest about the duplication it leaves. Rules. (1) The reachability gate is read BEFORE the edit, because 「fixing a bug in code nothing reaches」 and 「fixing a bug」 are different products and the user is buying a behaviour change, not a diff. (2) The do-nothing-adjacent option must say plainly that visible behaviour is UNCHANGED, so a correctness-only fix cannot be read as a delivered visual fix. (3) The in-place fix takes the CORRECT SIBLING as its reference and mirrors that formula exactly (the CPU Lucas-Kanade kernel), rather than deriving a fresh expression — a hand-derived version came out inconsistent with the CPU's luma central-difference and had to be rewritten. (4) When the pattern needed for the fix does not exist yet, the subagent's NOT FOUND is itself the design input: report plainly that no precedent exists in the subsystem and establish the pattern from the sibling path.
