# project-workflow
- The Reactive Event system (ReactiveEvents, ReactiveEngine, ArtifactReactionExecutor) is off-limits for modifications, improvements, or implementation proposals unless the user explicitly requests work on it. Do not touch it or suggest enhancements. Confidence: 0.85

- For developer branch naming in the parent-child repos, use a generic suffix (e.g. `codex/YYYY-MM-DD-dev` or just `codex/YYYY-MM-DD`) rather than a feature-specific name like `codex/YYYY-MM-DD-<feature>`. The branch should reflect ongoing development, not a specific milestone or feature set. If the user rejects a feature-specific name and picks a date-only alternative, use the date-only format. Confidence: 0.80
- Do not run build, tests, or formatting commands for the ArtifactStudio project unless the user explicitly requests it. Confidence: 0.90
- Do not commit or push to the parent/child git repos (Artifact/, ArtifactCore/, ArtifactWidgets/) unless the user explicitly asks; just stop at the file-edit step. Confidence: 0.85
- Before creating a new feature/widget/file, verify by exploration that an equivalent implementation does not already exist (under any name/alias) in the workspace; only proceed if the check is explicit. Confidence: 0.60
- When `git status` shows modifications to files outside the current task scope, treat them as the user's in-progress work; run `git diff` to understand intent but do NOT revert, edit, or commit those changes. Only touch files directly required by the current task. Confidence: 0.85
- The project is on Windows; `find` and `grep` are NOT available in shell. Use `findstr /S /N /C:"pattern" path` for text search, `read_directory` for directory listing, and `glob` for file pattern matching. Confidence: 0.75
- Use a dedicated git worktree for AI-assisted work sessions (e.g. `X:\dev\commandcode-wt-YYYY-MM-DD` on branch `dev/commandcode-YYYY-MM-DD`) instead of working directly on `main`. The main repo should be left untouched. Confidence: 0.80
- `write_file`/`edit_file` are restricted to the main repo workspace (`X:\dev\artifactstudio`) and reject paths inside the worktree. When asked to save to a worktree path, ask the user to confirm placing it in the main repo's `docs/reports/` (or similar) rather than retrying with shell heredoc. Confidence: 0.80
- For "large / 大量" utility/API proposals targeting `ArtifactCore` (e.g. string helpers, random/noise helpers), the user's typical workflow is: explore existing code first (depth: medium), then write a structured proposal markdown to `docs/planned/STRING_HELPER_PROPOSAL_YYYY-MM-DD.md` (or similar) with sections for current-state inventory, module groups labeled A-J, ~100 function signatures, priority levels (★★★/★★/★/○), test policy, and related files. Stay in proposal mode unless user explicitly asks to start implementation. Confidence: 0.60
- When the user requests milestone documents (マイルストーン), write them as detailed, thorough files with full phase planning, existing-asset analysis, design pillars, invariants/guardrails, and relationships to existing milestones. Save directly to disk. Do not produce short summaries when the user asks for 詳細 / しっかり / 詳細に. The user prefers comprehensive, time-invested milestone documents. Confidence: 0.75
- For analysis/investigation reports (ソース調査 / パフォーマンス分析 / 機能ギャップ調査), write thorough markdown reports to `docs/analysis/REPORT_*_YYYY-MM-DD.md` with full methodology, structured tables of findings (OK/PART/MISS counts), severity classification (重大度 S/A/B), prioritized fix recommendations, and connections to existing milestones. Follow the same comprehensive-investment pattern as milestone docs. Clean up temporary scan scripts (`_*.py`) after the report is written. Confidence: 0.70
- For empty/placeholder stub implementations (e.g. CSharpScriptEngine skeleton), do NOT propose deletion. Implement them instead when work on that area is requested. The user explicitly rejected a deletion suggestion and asked for implementation. Confidence: 0.70
- When implementation scope exceeds the session budget (e.g. requires full render engine, audio engine, etc.), explicitly propose a separate milestone ID (M-PR-XXX-N), implement a minimum viable alternative for the current session, and document the deferred work in the final summary. Do not silently skip features that the user asked for; surface the deferral. Confidence: 0.75
- When creating a new development branch in the parent repo (e.g. `codex/YYYY-MM-DD`), also create branches with the same name in all submodules (Artifact, ArtifactCore, ArtifactWidgets) so that simultaneous development can proceed under a unified branch naming scheme. Confidence: 0.60
