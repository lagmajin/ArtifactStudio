# task-preference
- A 「相等チェック/整合性チェックして」 whose findings close with a fix order already stated, answered by 「じゃあ簡単な修正を」, authorizes the previously recommended priority order — not a re-sort, and not a narrowing to one item. Applied 2026-09-28: the report ended 「優先度は 1 → 2 → 3 の順が妥当です」, the reply was 「じゃあ簡単な修正を」, and all four confirmed items were executed in that order with a `todo_write` row each (matching the existing 「簡単なものから修正して」 entry's easy-subset reading while confirming the assistant's own ranking carries the authorization). The 「簡単な」 qualifier scopes the work to fixes that need no design decision — items requiring structural change are excluded and named in the report with the structural reason (here: `depthTest`/`depthWrite` forced false in the renderer needs a DSV-binding restructure, and deleting dead subsystems needs a delete-vs-integrate call), not with 「大きいので後回し」. So the report's deferred block must state the specific blocker for each item it did not take. Confidence: 0.6
- A 「整合性チェックして」 that names NO target is authorization for the assistant to SELECT the target, and the selection criterion the user implies is **STALENESS** — 「最近いじってない部分」 — not the largest, riskiest, or most recently touched area. Accepted delivery: derive the choice from git history (a file that is an outlier inside an otherwise recently swept subsystem), state in one line WHY that file was chosen with its last-commit date, then run the full consistency audit and hand back a prioritized list. This is the same self-targeting delegation the user shows elsewhere (「次の仕事何がいいかな」 answered with a shortlist rather than a question), applied to audits: the standing expectation is a chosen target plus a completed pass, not 「どのファイルを見ましょうか」. Reassuringly, the report closed by asking which item to fix, so the delegation extends to the audit but not to the edits. Confidence: 0.55
- 「簡単なものから修正して」 sent in reply to a severity-ranked defect list with a closing fork (「#1 が費用対効果が高い。着手してよいか、それとも #2 の設計を先にするか」) authorizes the assistant's OWN easy-subset selection rather than the recommended item — the fix is to pick the mechanically-isolated ones, execute them, and name in the report both the items taken and the ones deliberately left for a design pass. Applied 2026-09-27 (preview disk cache): the report's top finding plus one [低] item were chosen and the two mid-severity findings (a missing RAM-side revision comparison, and gizmo-drag-time staleness) were left untouched with the reason each is not 「簡単」 stated concretely. Distinguish this from the form where the assistant already sorted its table easy→hard and the user adopts that order wholesale — here the assistant had recommended a DIFFERENT starting item and the user's phrase redirected the choice criterion to simplicity. The user's criterion is 「safe and self-contained」, so the selection test is: can it be done without a design decision that would have side effects? Confidence: 0.55
- A recommendation to re-enable a compile-time-disabled optimization is a HARD GATE, not a step-1 offer: the user remembers specific past failures by mechanism name and will override an otherwise-recommended action. Applied 2026-09-29 (SolidRect batch): the countermeasure list's #1 was 「`constexpr bool kSolidRectBatchValidated` を実行時フラグ化して ON/OFF フレームを比較」, and the reply was 「むかしSolidRectのバッチでうまくいかなかったのでそこはちょっと原因調べてから導入したい」 — diagnose the ORIGINAL regression before proposing introduction, not after. The accepted next step was a root-cause isolation pass whose first rung removed a variable (temporarily force the direct `DrawIndexed` path instead of the `>= N`-packet `DrawIndexedIndirect` branch), not enabling anything. Generalize: when a code comment records a specific past visual failure of an optimization (here 「swap-chain で clear-only」), treat that comment as a regression record to be EXPLAINED, and make the countermeasure sequence start with the smallest experiment that discriminates between the candidate hypotheses; the re-enable proposal comes last, behind the root cause. Confidence: 0.6
- When presented with a choice between stability/bug-fix work and new feature development, prefers new feature creation (新機能作成). Reconfirmed 2026-08-21: offered four ArtifactPr tracks — build restore (assistant-recommended), export implementation, composite preview (new feature), engine testing — the user picked the new-feature option (合成プレビュー) over the recommended build-fix prerequisite. Also defers test infrastructure and small cleanups: in the 2026-08-22 multi-select scope question the user selected データ整合 + プレビュー強化 but left GTest 追加 and 小口改善 (bin 管理・autoSave 整理) unselected. Same pattern again 2026-08-22 (variable expansion): chose only the core mechanism (展開エンジン＋Property フック, 評価時展開) and deferred env ファイル / 変数一覧 UI / ArtifactPr 対応 to a later phase — for big infrastructure features, core engine first, UI/peripheral integration later. Reconfirmed 2026-09-26: from a shortlist of implementable candidates the user took the recommended smallest win (wiring an already-implemented predicate) *and* a mid-sized feature (display-only viewer exposure post-process) in the same pass, skipping both the trivial one-liner (`static const bool` → runtime flag) and the large foundational work. So the selector is not strictly "smallest first" — it is "recommended first, plus at most one substantial item". And when the shortlist contains a zero-code option that stops a stale `Not Started` item from being re-implemented, the user takes that one *alone* and skips even the recommended code item — avoiding duplicate implementation of already-working code outranks picking a new feature (2026-09-26: chose only 「P1-12 の重複を文書で解消」 over the recommended ShowDiagonals one-liner and the P1-10 Clipping feature). Further reconfirmed 2026-09-26: after a report that ended with a 未対応 list plus a 確認事項 flagging an unverified assumption, the shortlist mixed one verification item with three real new features (10-effect preset wiring, LUTEffect GPU impl, a dedicated Color Wheels panel with an ASCII mock) — and the user took the verification item, marked 「(Recommended)」. So a clean-upe-your-own-work option presented as a peer choice does get picked over new features, and the recommendation marker appears to carry real weight in the `ask_user_question` form. Reconfirmed 2026-09-26 in a new form: when the assistant answered 「次の仕事何がいいかな」 with 「the build is the answer」, explicitly recommended *against* the most attractive new-feature candidate, and offered a menu, the user pushed back with 「新しい実装案とかだせないかな」 — so a build-first recommendation does not permanently suppress new-feature proposals; keep producing them and keep stating the build risk, rather than treating the build as the only available job. Confidence: 0.85
- 「副作用がない順に修正してくれ」 is a RE-SORTING directive, not an endorsement of the audit's own ranking: once a defect list is authorized for fixing, the user may order the work by **blast radius** — how much an unnoticed mistake would touch — instead of by severity. Accepted execution shape: invert the priority list and work ascending-risk (a localized predicate, a dead enum, an unreachable sentinel, a hit-order tweak), and leave for last the fix that reworks shared drag state or coordinate spaces, with one `todo_write` row per item, and state why the order was inverted so the sequence is not read as a re-ranking of severity. Corollary: do not ask 「どこから進めますか」 again after this instruction — the ordering criterion has just been supplied, and it governs the whole approved list at once. Applied 2026-09-27 (text Gizmo audit: six items executed P2 → P1 → P0, the two P0s last). Confidence: 0.6
- When a fix would surface many already-implemented items at once, the user chooses EXPOSE-EVERYTHING over a verified-subset gate, and prefers the pure-exposure scope over bundling new code with it. Applied 2026-09-27 to 57 effect-catalog entries that were registered in the service but unreachable from the Inspector picker: offered 「確認済みのみ出す（GPU 要件を実測した effect だけ出し、残りは Not ready でグレー化）」 vs 「全部出す（実装済みのものを隠す理由はない。CPU フォールバックが働けば実害は限定的）」 marked (Recommended), and the user took 全部出す — accepting that some entries may visibly do nothing, with the unmeasured `supportsGPU()` behavior recorded as a 未確認 acceptance item rather than used as a reason to gate. In the paired scope question the pick was also the exposure fix ALONE (1 file, low risk) over 「57件 + 新規 AE 歪み 4 種」 and over 「新規 4 種のみ」. Practical consequence: do not manufacture a verification pass the user did not ask for in order to justify hiding entries, and do not bundle a new-feature build into a make-existing-visible change; ship the exposure, document what is unmeasured, and let the next pass add features. Confidence: 0.6
- When picking between two technology options, the user often adds a CONSTRAINT that reframes the pick into a gradual-adoption directive rather than a replacement: 「じゃあ１で　Qtは現状使いつつharfbuzzの実装育てたい」 (take option 1, but keep using Qt for now and grow the HarfBuzz implementation). The accepted shape is a PARALLEL implementation: the new path becomes the primary inside its own abstraction, the old path remains a total fallback for every case the new one cannot yet handle, and NO consumer call site is switched yet — the cutover becomes a separate stage gated on a dual-run comparison. Ship the parallel stage on its own rather than bundling the switch, and state in the report exactly which call sites still name the old backend (here `ArtifactTextLayer.cppm:1158`/`:3487` and `DiligentImmediateSubmitter.cppm:178`) so the user can see that existing rendering behavior is unchanged. Applied 2026-09-27 (HarfBuzz shaping backend). Confidence: 0.6
- When a feature-expansion request is genuinely multi-directional, the user accepts the recommended narrow direction AND a groundwork refactor as a paired first phase. Applied 2026-09-27 to 「２Dデフォーマの機能拡充を」: the assistant entered plan mode, dispatched parallel `explore` agents to inventory the gaps, and offered three directions (fill holes in already-working features / AE-style free lattice mesh warp / wire Rig2D SkinMesh to 2D layers) plus a second question on whether to consolidate the 20 duplicated `mode → controls-array-key` branches before adding any mode. The user took BOTH recommendations — the low-risk hole-filling as the scope, and the branch consolidation as the thing to do first, explicitly because adding a mode would otherwise multiply 20 hand-edits into 55. Generalize: when a survey reveals that the requested expansion is gated on a duplicated-branch tax, present 「consolidate first」 as its own question (it is a real fork with a real price either way) and expect it to be taken; and when a candidate is 「implemented but has no UI 導線」, that is the highest-value pick because it is the only one with zero new risk. The report then owes a 未対応 block naming the deferred directions and their real blockers (the free lattice needs non-rectangular topology support the Shape path lacks; Rig2D's SkinMesh generation code does not exist). Confidence: 0.5
- For a broad NEW feature area the user scopes the start down to a single self-contained, low-risk sub-feature instead of kicking off several at once: offered four accessibility axes (viewport magnifier / screen-reader depth / keyboard-only core editing / reduce-motion) with multi-select explicitly allowed and a 推奨 marker, the user picked only the recommended, self-contained viewport magnifier (2026-09-21) — chosen partly because the settings and UI for it already existed and only the drawing consumer was missing. This is distinct from audit-generated gap/fix shortlists, where the standing default is 「全部で」/「じゃあ修正を」 (handle all of them). Confidence: 0.5
- The user sometimes replies by pasting ONE paragraph of the assistant's own report verbatim (the exact bullet, citations and all) and appending 「これはどうしたらいいの」. That is a drill-in directive, not a re-ask: the answer must address exactly the pasted claim, in the depth the claim's own mechanism warrants, and must NOT re-deliver the surrounding report or its other findings. Read the pasted bullet for the specific sub-question inside it (here: not 「how do I batch better」 but 「what flushes the accumulated batches and why is SolidRect's own batch disabled」), and the answer's value is in closing the loop on that mechanism with file:line rather than restating the conclusion. Confidence: 0.55
- A 「<X>だった　それを調べて」 means: dig into exactly that ONE of the systems the previous report enumerated, not restart the survey and not re-litigate the others. Applied 2026-09-27: after a three-system cloner report (clone layer / cloner component / dead `CloneGenerator`), 「クローンコンポーネントだった　それを調べて」 selected the middle system. The report shape: open with the 訂正 if the earlier report was wrong about this specific target, then answer only the asked question (its render path, its extension point, its mode table), and keep findings that survive in the OTHER systems out of the remaining-weaknesses list — they are not what was asked for, and repeating them dilutes the correction. Confidence: 0.55
- Pasting the report's OWN residual block verbatim (the 残る未解決 / 未確認 bullets) and appending 「これをなおして」 is authorization to fix exactly those items — all of them, in one pass, with no re-scoping and no re-asking. Applied 2026-09-29: the two bullets pasted were 「ブレンドモードは依然として無視される。blendGpuLayerIntoAccum を bypass したままだ」 and 「マスク描画は毎フレーム CPU（cv::Mat + QImage）… GPU 化は未着手です」, and the accepted delivery was a `todo_write` row per item, both implemented, and a closing 未確認 block. The important second half: the pasted text carries the ASSISTANT's own diagnosis and goal-setting, and that is NOT automatically the implementation plan — here 「GPU 化」 was falsified by reading the named asset (`MaskCutoutPipeline` is a QImage-input, scene-application API, not a GPU rasterizer), so the correct fix targeted the actual cost (eliminating the per-frame regeneration via a content-keyed cache) and the report opened by stating the reinterpretation. So: fix what the user pointed at, verify the premise it carries, and if the premise is wrong, say so in the first line of the report and deliver the fix for the real cost — do not implement the literal goal word, and do not stop to ask. This is the imperative sibling of the existing 「これはどうしたらいいの」 drill-in rule. Confidence: 0.6
- Corollary, learned the NEXT session: a residual item's ORIGINAL goal word survives the reframe and will be asked about again verbatim. Applied 2026-09-29: after the assistant falsified 「GPU 化」 and delivered a content-keyed cache instead, the user's next message — in a fresh session, with no reference to the correction — was 「マスクのラスタライズってGPU化できるの？」, the exact wording of the 未解決 bullet and not of the delivered fix. So a reframe must be answered at the level of the original word, on its own terms, with the reframe demoted to one supporting sentence inside that answer; never open by restating 「GPU 化ではなく〜が正解でした」, and never treat the return of the old word as the user having missed the correction. The durable reading is that the 未解決/未確認 block is a QUEUE the user reads literally, so every entry in it should be phrased so that the question it invites is the one that should be asked. Confidence: 0.5
- A non-contiguous numbered selection 「じゃあ１と３」 is authorization for exactly those two items, and when the list MIXES a few-line defect fix with a heavy new-feature direction the selector reads as interest/topic, not cost — do not fold the skipped middle item back in, and do not re-sort. Applied 2026-09-29 to a 3-item 着手順 where #1 and #2 were both few-line UI-wiring omissions (View ▸ zoom actions never `connect`-ed; Layer ▸ 分布 submenu built but never `addAction`-ed) and #3 was a whole missing capability (mask compositing / mask tracking): the user picked #1 and #3, dropping the same-cost #2, and the accepted follow-up shape was to implement the cheap fix first, report it, and then offer the two halves of #3 as their own fork (「どちらから着手しましょうか」) rather than starting the large one immediately. So a selection naming a big item means "this direction, in this order" — the concrete sub-scope of the big item is still the assistant's to put back to the user. Reconfirmed the same day in the single-number form: 「じゃあ３」 naming one whole missing-capability area (mask compositing / mask tracking) is authorization for that area outright, and the sub-scope fork it triggers is an `ask_user_question` whose options each carry an ASCII preview of the resulting panel/menu plus a one-line reason, with the (Recommended) marker placed on the half that RIDES AN EXISTING MECHANISM (extend the tracker's per-target apply structure) rather than the half needing a new algorithm (boolean mask geometry bridged through rasterize → bitwise → fromAlphaMask). The recommendation criterion is extension-point reuse, not size. Confidence: 0.55
- Named form of the same directive — 「じゃあ<X> と<Y>」 naming two items from the assistant's cost-tiered proposal (applied 2026-10-01: one recommended 中コスト item plus one 忘れられがちな穴 item) — authorizes exactly those two, and when the two are INDEPENDENT areas the accepted execution shape is PARALLEL in one pass: two investigation `explore` subagents dispatched in the same turn, an interleaved `todo_write` ladder spanning both areas (調査→実装 per area, then a shared 検証 rung), and both closed in the same final report. The user raised no objection to the parallel shape, so the sequential cheap-fix-first reading is not mandatory when the pair is independent. Confidence: 0.5
