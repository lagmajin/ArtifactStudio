# communication-integrity
- Always read actual source code before answering — never rely solely on documents, speculation, or unchecked assumptions. If something is unverified or unclear, explicitly state 「未確認」rather than guessing or presenting speculation as fact. This applies to ALL responses, not just feature-gap investigations. The user issued this directive after being told that MFR was "not implemented" (which led to a full milestone being written), when in fact MFR was already implemented with farm distribution + checkpoint recovery — the assistant had trusted its own assumption rather than reading the source first. Applies equally to explore-subagent output: load-bearing claims returned by dispatched agents must be re-verified directly in source (grep/read citing file:line) before being presented as findings — applied 2026-08-21 in the offline-rendering audit (confirmed `const bool useMfr = false;` at ArtifactRenderQueueService.cppm:6660 and the QPainter fallback before reporting them). Reconfirmed again 2026-09-27 during a cross-repo unification: two separate dispatched-agent claims were each wrong on a *line number*, not just on a conclusion — 「`CMakeLists.txt:145` に QADS リンク」 when the file is 153 lines and `:145` is a `target_compile_definitions` call, and 「永続化されていない」 when the save/restore pair is called from both the constructor and `closeEvent`. Both were caught only by opening the cited file with `read_file`, and both were then written into the plan's 訂正 section and into the Insight.md 訂正した誤情報 bullet. Confidence: 0.95 the assistant paused mid-implementation to verify its own assumptions against actual source before writing dependent code — whether the JSON helpers lived in an anonymous namespace vs external linkage, which CMake targets actually contain Core's Command/Audio/Video modules (split STATIC libs, not the aggregate), and exact AudioMixer/AudioBus signatures. Extended 2026-08-22: this duty covers the assistant's own accumulated records too — when fresh exploration contradicts a previously recorded claim (the foundation-class audit found prior 「RandomStream 統合済み」 note contradicted by grep showing 0 external usages + mt19937 remnants), surface the contradiction openly and mark the item 要再確認 instead of repeating the stale record as fact. Confidence: 0.95 The corollary for statements already made TO the user: a premise voiced in a report or in an `ask_user_question` option's description is a claim exactly as much as one written in a code comment, so when source later disproves it, retract it in the first line of the next report rather than quietly shipping the better version. Applied 2026-09-27: an option priced a render optimization as 「必要: solidRect シェーダーの頂点色補間をCB側へ。PSO/シェーダー差替」, and the delivered change needed no shader or PSO change at all because the input layout never read the vertex color — the report opened by naming the overturned premise. A sixth form, and the one that costs the most if missed: a *verifying subagent's* disagreement. Applied 2026-09-27 building 4 new effects: a dispatched read-only agent reported the CMake registration was incomplete and that `import` resolution would likely fail; the assistant opened `scripts/check_source_manifests.py` and the `ARTIFACT_EFFECTS_MODULES` base list directly, found the agent had only checked the pack list, fixed the real gap, and then stated the correction plainly in the closing line — 「検証 agent が『import 解決に失敗する可能性が高い』と報告しましたが、自分が実ロジックと既存 pack の登録状態を確認して修正しました」. The general shape: when a subagent's verdict and a repo tool's output disagree, the tool and the cited file win, and the report says so rather than leaving the user to wonder which of the two to trust. Confidence: 0.95
- The cheapest way to falsify a subagent's 「defect」 is to check whether the defect is REACHABLE at all, before opening the cited lines. Applied 2026-09-27 (2D-deformer audit): the agent reported 「Shape レイヤーの Undo が必ず失敗する」, and the disproof was the tool's own entry-point signature — `ArtifactPuppetTool` only ever receives an `ArtifactImageLayer*`, so a Shape layer can never reach that Undo command and the claim is structurally impossible. The second falsification in the same pass went the other way: the agent reported 「ピン種別は Ctrl/既定の暗黙切替のみ」, and the actual code at `ArtifactCompositionRenderController.cppm:26641-26647` binds all four types (Ctrl/Starch, Shift/Bend, Alt/Overlap, none/Position) with type names in the HUD. Two of four P0 items were false, so budget the re-verification as a real cost, and when a claim is dropped say so in the deliverable's 訂正/未確認 block with the reason — the user reads that block to calibrate trust in the rest. Confidence: 0.6
- The mirror-image failure, and it is the assistant's OWN claim rather than a subagent's: **「a value is computed and fed to X, therefore the behavior is unimplemented」 is a defect claim about a consumer, so trace X to its effect before writing it up.** Applied 2026-09-27 to the 2D deformer: an earlier report asserted 「`Overlap` ピンは no-op — `zDepth` は三角形ソートにのみ使われ、前後 Occlusion に影響しない」 and floated a fix (enable GPU depth test) plus a 「UI 上で『未対応』と明示する」 fallback. The read had stopped at the assignment; the value's consumer (`lp->triangleOrder`, walked by the alpha-blend draw loop) WAS the occlusion mechanism, so the feature worked. The tell that a claim was written from a partial read rather than from evidence: it names an internal variable and asserts its *purpose* without citing the line that consumes it. Enforce the inverse rule before a defect goes into a report — follow the value to its terminal effect (which draw order / which buffer / which branch), and if the effect is indirect, say so explicitly rather than labeling the feature a no-op. The retraction then costs the user nothing but a line, whereas the false finding had already been priced as future work and handed to him as a decision. Confidence: 0.55
- When the user refers to a feature by a UI/Japanese display name (e.g. 「ミキサーレイヤー」) OR by an informal abbreviation/acronym (e.g. 「VP操作」), do NOT assume what the term maps to or that a matching class exists in source — grep the term itself plus likely expansions/English equivalents (Mixer/MixerLayer; VP → Viewport) across code and docs before planning. If the expansion resolves unambiguously in code, state the interpretation explicitly and proceed with that reading; if the name maps to no class, surface the mismatch and ask the user to disambiguate which code entity they mean (structured options) instead of guessing. Applied 2026-08-22 when 「ミキサーレイヤー」 turned out to have no corresponding image-layer class (only AudioMixer / an unimplemented ColorNodeType::LayerMixer stub / LayerBlendPipeline), and the assistant asked a disambiguating question before judging the 昇格 feasibility. Applied again 2026-09-02: 「VP操作」 was resolved by grepping `\bVP\b` across .ixx/.cppm/.cpp/.h (found = Diligent `Viewport`) plus TextViewport variants, with the interpretation stated to the user before investigating text-layer viewport interaction. A third outcome also exists — the name resolves to a *shared algorithm library*, not to any effect: 「カラーコレクションエフェクト」(2026-09-26) turned out to be no effect at all, only the CMake static library `ColorCollection` (`ColorCollection.ColorGrading` module) plus one differently-named consumer effect `ColorWheelsEffect`. Correct handling is to open the report by correcting the premise (「『Color Collection』という名前のエフェクトは存在しません」), then answer under the interpreted reading anyway — implemented-assets inventory followed by a file:line table of real defects in the library and its consumer — rather than stalling on a disambiguation question. Confidence: 0.6

# cost-benefit-prioritization
- When deciding which types in the codebase to extend with operators/utilities, prioritize based on cross-codebase usage footprint, not just whether the type is a color/vector/etc. Types used only as local variables in a single translation unit (e.g. HSVColor/HSLColor used only inside ColorConversion) are low value for operator expansion. Types heavily used across multiple subsystems (e.g. DynVec2/3 used throughout AnimationDynamics) get higher priority. The user accepted this cost-benefit analysis — "value of wide cross-cutting impact" — without objection. Confidence: 0.70

# cppm-modules
- In C++20 module files (.cppm/.ixx), do NOT put `#include` directives in the module purview (after `module X;`). All includes must go in the Global Module Fragment (GMF) between `module;` and `export module X;`. The only exception is TBB includes which should be placed in GMF with all other includes, NOT in the purview. Confidence: 0.80

# project-submodule-boundary
- Do not modify, commit, or push the `ArtifactWidgets`, `libs/...`, or `third_party/*` submodules unless the user explicitly asks; treat them as read-only/external. New UI widgets are first placed under `Artifact/` and only promoted to `ArtifactWidgets/` later. When a feature looks like it needs submodule work, verify the *consumer-side* API before assuming so — if the public interface takes a whole-frame object (e.g. `updateFrame(const QImage&)`) and the caller already holds the full frame locally, a rect-limited feature (ROI) is achievable with a single `frame.copy(x,y,w,h)` at the call site and the submodule boundary is never crossed (2026-09-26, scope ROI). Consequently prefer a CPU-side parent-repo path as stage 1 and defer any GPU/submodule version to a later stage gated on measurement, instead of blocking on a fork/patch decision up front.
