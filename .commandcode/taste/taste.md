# feature-request-framing
- When the user names an EXTERNAL product as shorthand for a capability bundle (「ResharperやVisualAssistみたいな機能ほしい」, and by extension Figma/Blender/Nuke-style references), the name is not one feature — it is a bundle. Do not implement your own guess of what that product means. Instead: (1) first ground the request in what the local engine can actually support (read the parser/evaluator data model — does the AST carry source offsets, is arity/type recorded anywhere, does a structured diagnostics type exist) and report the gaps that determine cost; (2) then decompose the product into 3–4 concrete capability groups and present them as a structured `ask_user_question` multi-select, each with a one-line description plus an ASCII preview of the resulting UI and a note of what must be built from scratch. Do not ask which single feature of ReSharper they mean — the user is delegating that decomposition. Applied 2026-09-26: decomposed into ① 署名メタデータ基盤＋型付き補完＋シグネチャヘルプ ② 診断強化（問題一覧/位置付きエラー） ③ ナビゲーション/Pick Whip ④ フォーマッタ/クリーンアップ, paired with a 対象 question (live Expression editor vs a not-yet-existing script editor). Confidence: 0.6
- A vague brainstorming prompt of the form 「<category>追加案あるかな」 asks for NEW candidate proposals in an already well-populated category, and it is a request for ideas, not for an audit or a verdict. Answer in chat with a cost-tiered candidate list. The tiers that work: ほぼゼロコスト (a shared helper/primitive already exists, so the item is a thin wrapper or an enum extension) / 中コスト (shader + a named existing sibling effect to copy as a 雛形) / 忘れられがちな穴 (features that are implemented but unreachable from the UI, or an empty UI shim that makes a whole surface look present) / possibly-a-bug (items that look implemented but are excluded from the GPU path, with a note that deleting them is better than keeping them). Every candidate carries its hook point with file:line, and each uncertain one is marked 未確認. Close by naming the recommended default and saying which items belong to a different subsystem and should be cut into their own pass. Applied 2026-09-27 (「画像エフェク追加案あるかな」 — 130+ effects already exist, the holes are AE's Distortion family and Stylize). **Reconfirmed on a DIFFERENT domain where the same shape held and one new rule appeared (2026-10-05, 「オーディオエフェクトってまだたりないかな」): the same four tiers came back with the same headings, so the tier vocabulary is the reusable half — and the new rule is that a candidate list over an effect family must ALSO surface a PERSISTENCE defect as its top recommendation, ranked above every feature addition.** The loader found `AudioBus::fromJson` writing the `effects` array while its own comment admits the rebuild is 「loaded externally using the manager+factory pattern」 with no such code, so save→reopen can drop the whole FX chain; that item was placed 第1便 alongside two new effects precisely because 「UI追加ではなく直し物」 outranks 「effect 増えた」, and it was marked 未実測 rather than asserted. Two companions. (1) **Per-effect cost must be quoted as an EDIT COUNT derived from the framework's seams, not as 「安い」** — here 「1エフェクト = .ixx 1枚 + .cppm 1枚 + 登録1行 + CMake 2行」 is only defensible because the registry list, the menu enumeration (`AudioMixerWidget.cppm:456-474`) and the auto-generated parameter UI from `getUiParameters()` (`:396`) were all read; a reader who cannot see the seams cannot know whether the NEXT effect costs the same. (2) **A candidate's UI availability can depend on WHICH REPO's base class it derives from, so a working Core-side effect is still not shippable as-is** — the seven app effects derive from `ArtifactAbstractAudioEffect` and the Core ones from `ArtifactCore::AudioEffect`, so the widget's `dynamic_cast` at `:394` returns null and no controls appear; the honest description says the near-zero-cost candidate needs a one-file adapter and is therefore 「ゼロコストではないが小さい」 rather than 「ほぼゼロ」. **A second increment, for the case where the target is a SEPARATE PROCESS rather than a code family** (2026-10-04, 「このProxyWorkerを機能強化できそうか」): 「<component>を機能強化できそうか」 is a feasibility-plus-candidates request, and the answer must cost-tier the candidates AND label each one on two axes beyond implementation cost — **which SIDE it lands on** (host-only / worker-only / both) and **whether it changes the wire protocol or its version**. For an out-of-process helper that is the dominant risk axis: the top-ranked candidate was chosen precisely because it closed inside the host app, touched neither the worker binary nor `protocolVersion`, and therefore needed no compatibility story — while the worker-side candidate it outranked would have required a protocol field addition. So the recommendation criterion for this class is 「effect ÷ (cross-process blast radius)」, and the report should say plainly when a candidate is host-side-only because that is what makes it cheap. Supporting detail worth carrying: a candidate list is only defensible if the worker AND its host-side driver were both read, because the cheapest wins (batching, parallel launch) live in the host and are invisible from the worker source alone. Confidence: 0.45 **One more ranking axis, and it outranks cost: a candidate whose ABSENCE renders the already-delivered batch non-functional.** Applied 2026-10-06 to the ArtifactScript host API, where the preceding pass had shipped `normalize` / `mix` / `dot` as host functions and the follow-up 「他のAPIいるかな」 found the language has no `vec3(...)` literal syntax at all — so those three shipped functions were unreachable from any script line. The candidate list therefore led with the literal-syntax gap, the assistant's stated reason being 「vec リテラルが致命的（既存 API が無意味）なので最優先」. So when the candidates are proposed for a surface this session (or a recent one) just extended, the first question is not 「what else could be added」 but 「can anything the last batch added actually be CALLED?」 — a function whose arguments cannot be written in the language is a null feature. This is the same shape as the persistence-defect rule above (a fix outranks an addition) but keyed on the PREVIOUS batch rather than on user-visible data loss, and it is invisible to cost tiering because the missing piece is a syntax gap in a file the last pass never opened. Confidence: 0.6
- A one-line mechanism proposal — 「<X>で<Y>するっていう仕組み考えた」 — is a MECHANISM, not a feature request, so the first deliverable is an infrastructure check that tells the user how much of it is already built, and the answer is frequently 「半分は既に実装されてます」 rather than a greenfield plan. Applied 2026-10-06 (「ペンタブでモーション描く」): three parallel `explore` agents over (a) pen/tablet input plumbing, (b) the motion/keyframe system, (c) path & multi-frame compositing came back with `ArtifactMotionSketchTool` already recording stroke+time samples via `QElapsedTimer`, `tabletEvent` already forwarding pressure/tilt into `ArtifactBrushTool::setPressure/setTilt`, and `AnimatableTransform3D` already carrying an editable spatial Bézier with orientation — so the honest report was 「インフラは無い、すでに○○」 plus the ONE real hole the proposal implies (wall-clock recording does not match the animation's duration). Three rules. (1) The lead sentence of the report is the EXISTENCE VERDICT plus the three or four file:line that already carry it, because the user is testing an idea against the codebase, not asking for an estimate. (2) Name the existing mechanism the proposal should RIDE, and price the new work as a delta on it — the value here was 「MotionSketch の addSample と BrushTool の pressure 配線が伸びるだけ」. (3) The residual gap the idea exposes (here the wall-clock time base) is a separate finding and belongs in its own bullet, because it is often the more valuable output than the feature. The variant decomposition then goes through `ask_user_question` as usual, each option carrying an ASCII preview of the resulting data shape plus a 新規 storage: ゼロ / ゼロコスト寄り line. Confidence: 0.5
- The same shape with a CONCRETE EXAMPLE appended (「<surface>のサポート拡大ってなにがあるかな　<rawタイプとか>」) does not narrow the question — the named example is a SPHERE PROBE, not a selection, and the answer must still be a ranked candidate list in which that one item receives an explicit verdict, including 「defer it, and here is the one fact that would settle it」. Applied 2026-10-07 (file import): the user named カメラ RAW and the report led with the fact that LibRaw is referenced zero times repo-wide while OIIO (already linked) ships a libraw plugin whose build-time feature state was unverifiable because `out/vcpkg_installed` was not laid down — so RAW was ranked LAST on the stated ground that the answer may already be yes, with the single command that would settle it named and the licensing question (GPL/LGPL) separated from the code cost. Naming the example explicitly is worth more than burying it: the user learns whether their own guess was cheap or expensive without having to infer it from the tier ordering. Confidence: 0.5

# cost-benefit-prioritization
- When deciding which types in the codebase to extend with operators/utilities, prioritize based on cross-codebase usage footprint, not just whether the type is a color/vector/etc. Types used only as local variables in a single translation unit (e.g. HSVColor/HSLColor used only inside ColorConversion) are low value for operator expansion. Types heavily used across multiple subsystems (e.g. DynVec2/3 used throughout AnimationDynamics) get higher priority. The user accepted this cost-benefit analysis — "value of wide cross-cutting impact" — without objection. Confidence: 0.70

- A new UI toggle for an existing tool belongs in an EXISTING Display-style menu (with `polishEditorMenu`, a submenu when the tool needs more than one entry), persisted via `LayeredConfigStore`, and defaults OFF so the current behavior is unchanged. Applied 2026-10-06 adding 「Motion Sketch ▸ Pen Pressure to Opacity」: the pass explicitly rejected adding a hardcoded key because AGENTS.md requires new bindings to go through `ShortcutBindings` (which lives in the child repo), so the menu toggle was the rule-compliant route. Two companions that made it complete rather than nominal. (1) Writing the setting without a READ-BACK is a one-way persist — the pass grepped for the sibling MotionSketch keys (`SampleRate` / `ShowWireframe` / `ShowBackground`) and found they were SAVE-ONLY, so the new key got a restore path the existing ones lack; set `setChecked` AFTER the `connect`, so the restore does not re-enter the handler. (2) A hot-path HUD readout is the cheap way to make an invisible option observable: the existing motion-sketch HUD line gained a `P:%6` field showing the live pressure value (or `OFF`), and the existing format string was widened in place on ONE line rather than reflowed, to respect the hot-path rules. Confidence: 0.5
- A terse 「<X>で<Y>」 reply answering a variant-decomposition `ask_user_question` selects that variant outright — no re-ask, and the unselected variants are not quietly folded back in. Applied 2026-10-06: the pen-tablet idea had been decomposed into four recording modes (velocity-profile mapping / refine the existing MotionSketch tool / draw curves in the Graph Editor / frame-crossing roto), and the reply 「VP で描く、筆圧→透明度。了解した」 picked the narrowest reading of the second option plus its concrete parameter assignment (pressure drives opacity), so the pass went straight to `todo_write` on the implementation. Naming the ASSUMPTION in one line before the first edit is what makes this safe: the response had to state that the pen pressure path is unconditionally already wired (`pressureAffectsOpacity/Size/Flow` exist on the brush tool), so the work is an extension of the existing path rather than a new input route. The unverified premise (whether `tabletEvent` actually fires under the Win32 native path, since `WA_NativeWindow` + a `WM_LBUTTONDOWN`-only `nativeEvent` switch has no `WM_POINTER*` case) belongs in the report's 未確認 block, not as a question back. Confidence: 0.5

# cppm-modules
- In C++20 module files (.cppm/.ixx), do NOT put `#include` directives in the module purview (after `module X;`). All includes must go in the Global Module Fragment (GMF) between `module;` and `export module X;`. The only exception is TBB includes which should be placed in GMF with all other includes, NOT in the purview. Confidence: 0.80

# language
- Communicates in Japanese and expects responses in Japanese. Confidence: 0.85
- A terse 「<verb>」 plus a NUMBER (「じゃあお願い１を」) selects that numbered item from the assistant's OWN report — even though no `ask_user_question` was ever issued, and even when the report expressed the ranking as prose headings (「第1便は DPX」) rather than a numbered list. The number resolves against the report's stated recommendation order, so the correct move is to `todo_write` that item immediately: no confirmation question, no re-derivation of the ranking, and no proposal of the item ranked second. The follow-through owes one line naming the assumption the recommendation rested on, because the ranking was the assistant's and the user is buying the item, not the argument. Confidence: 0.5
- The session language governs INTERSTITIAL lines too — the one-line 「〜します」 before a tool call is something the user reads, not a private step. Keep it Japanese, keep it to the single action being taken, and never let a stock or English phrase slip into a Japanese turn: the user sees the prose, not the tool call, so a line in the wrong language or describing work that is not happening reads as a broken tool rather than a progress note. When the user asks a direct factual question, the turn must end with the answer stated in that language, not with a promise to answer. Confidence: 0.5
- The session language governs a LONG implementation stretch too, not only the interstitial one-liner: during a multi-edit pass the narration drifted entirely into English (「The hardcoded list is the problem. Let me check what factory already exists…」「Before editing, I need to confirm `EffectID`'s constructor accepts a `QString`」「I have everything I need. Implementing the fix now.」) in a session with no English request anywhere, while the delivery report stayed Japanese. The drift starts at the SECOND or THIRD consecutive read-then-edit step, so the check is per-turn rather than per-session: any narration line must be Japanese in a Japanese session, even when the code, the tool arguments, and the diff are all English. **Reconfirmed 2026-10-04 on a ~20-step implementation pass, which pins the trigger: the narration was English for nearly every step (「I introduced a bogus type `QFormFileInfo` by accident. Let me fix that immediately.」「Now let me find all remaining references to the old members」「The file got locked, likely a transient issue. Let me retry.」「Let me re-read the exact current state of that block.」) with two Chinese lines mixed in (「既然直接开工」「现在开始改造并 Slots 構造」) — while every code comment, every tool argument and the final report came out clean.** So the drift is not a function of session length, and it does NOT contaminate the deliverables; it is a per-turn lapse that a clean report does not retroactively excuse. The practical check is therefore at each narration line, not at the end of the turn. **Reconfirmed again 2026-10-07 on a two-item fix pass, and the vocabulary of the drift is the useful part because the previously-seen language list was not a predictor: a Polish fragment spliced mid-clause (「両self 依赖Czają więc」), a Korean predicate fragment (「プリフライトの警告 مكان 찾기s」), Chinese standing where a Japanese particle belonged (「この-imgOpts は AOV 専用なので、通常出力的 imgOpts 应该在 else 侧にある」), and — the shape that survives a skim because the sentence is otherwise fluent — an ENGLISH VERB FUSED INTO A JAPANESE NOUN (「`class ... Impl {` を消weaponました」). The same pass carried the drift into the `todo_write` payloads themselves: six consecutive `activeForm` strings used 的 in place of が/を, so the sweep has to cover the task list as well as the prose.** Confidence: 0.55
- The user's requests are often a bare noun phrase that may be CUT OFF mid-sentence (「えっとMCPサーバーの整合性を」), so the trailing phrase — not a complete sentence — is the entire instruction. Read it as subject + implicit verb (「<X>の整合性を［調べて］」) and resolve the missing OBJECT (which surface) with a SINGLE `ask_user_question` naming the concrete candidates rather than guessing: here 設定・登録状況（settings.json の登録内容と実起動可否の突き合わせ）/ コード側の実装 / CLI 側の設置状況. Pair the one-line 「切れています」 observation with the question in the same turn instead of stopping there — the fragment still identifies the subject reliably. A fragment whose TAIL is a list of VERBS rather than a noun needs no disambiguation question at all: 「えっとレイヤーコンポーネントでスクリプト追加と削除　実行などができるか調べたい」 names its subject unambiguously and the 「など」 marks the list as non-exhaustive, so the verbs themselves become the report's axis — one verdict row each, never a single 「できます／できません」, because in a partially built subsystem 追加・削除・実行 routinely disagree (API あり/呼び出しなし, エンジンあり/接続なし, UI 部分的). Read 「など」 as a licence to add a verb the user did not list, not as a reason to ask what else they meant. Confidence: 0.5

# project-direction

So text-layer work is judged on script coverage (bidi, vertical, Indic reordering, emoji/ZWJ, per-script font fallback) and on whether the implementation *admits* the scripts it cannot handle, not on Japanese rendering quality. - The in-house scripting language **ArtifactScript** (`ArtifactCore/src/Script/ArtifactScript/`) is a strategic investment: the user wants to evolve it (「自作言語...これでいきたいなぁ」) rather than rely on embedded third-party engines (AngelScript / CSharpScriptEngine).
