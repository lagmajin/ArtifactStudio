# ux-design-philosophy
- When an approved design mock already exists, the user wants it iterated, not replaced: 「すでにあるならVer2みたいな感じで」. Keep the approved skeleton (e.g. the 3-pane Places / tile-grid / inspector layout of `docs/design/project-open-picker/`) and spend the version bump filling in the *information density* the runtime is missing (per-project composition preview, resolution/duration, health dot, composition/asset counts, external-source warning, Favorites, grid/list toggle) rather than proposing a layout for a different workflow. Offered 3 axes (density fill / workflow redesign / multi-project batch open) plus an image-count question, the user took the recommended density-fill option with a candidate + before/after pair. Corollary: a freshly generated mock ships as 未採用 until the user approves it, and the mock must show the house visual language (charcoal surfaces, cool-blue primary accent) rather than raw Qt default widgets — the current screen looked 「みすぼらしい」 precisely because it fell back to plain `QFrame::StyledPanel` / `QListWidget::IconMode` styling. Confidence: 0.6
- For an already-adopted UI mock, successive versions keep version-bumping the *same* concept in the same `docs/design/<topic>/` directory (Ver2 → Ver3, e.g. `…-v3-candidate…png` / `…-v3-before-after…png`) rather than starting a new design (「うんVer3も出してみてくれるかな」). Later bumps trend toward a *smaller* delta from the current runtime — Ver3 was taken as the 「最小改修案」 (keep the approved 3-pane skeleton, swap only the generic per-project icon for a real composition thumbnail) — and when the assistant presents axes (A minimal改修 / B workflow redesign / C multi-project batch) the user picks the lowest-implementation-cost one. When asked which direction a not-yet-drawn version should emphasize, the user may answer 「一応画像出してみて」: produce the concrete candidate image first and choose after seeing it, rather than settling the direction in the abstract. Confidence: 0.55
- The user repeatedly double-checks that mockup/image generation is actually possible (「画像生成できる？」, 「画像生成行ける？」) and the answer must state plainly what is available: hand-coded PIL/`ImageDraw` UI mockups (rectangles/lines/text placed at fixed coordinates by a `generate_*.py` script), explicitly NOT AI/photorealistic image generation — for real renders/textures/concept art the toolchain has no generator, so those must come from an external tool or Artifact's own renderer. Confidence: 0.5
- Prefers innovative UX interactions with "wow factor" over standard drag-and-drop / conventional patterns. When asked for feature proposals (especially D&D/UI interactions), the user expects the assistant to brainstorm creative, surprising ideas that make users say 「そんなことできるの？」(you can do that?!), rather than straightforward conventional implementations. The user explicitly rejected a standard "drag effect from palette to layer" milestone as too plain/obvious (「地味だ」) and asked for more revolutionary interaction designs. Confidence: 0.80
- Prefers feature designs that are mode-rich (モードがいっぱいある) with many variations over a single-purpose tool — when brainstorming enhancements for the plane/solid layer, the user found the idea of "many modes" appealing (「モードがいっぱいあると面白そう」). Confidence: 0.55
- Asks for additional variants of existing UI behavior as opt-in options (「〜もほしい」) rather than replacements — the current behavior stays the default and the new variant becomes a switchable, persisted choice rather than changing the look for everyone. Applied 2026-09-22: 「VisualStudioみたいなタブエリアが下のバージョンもほしい」 resolved to a per-tab-area top/bottom placement toggle with top as the default and the choice saved per area. Confidence: 0.55
- Background/parallel work must never hijack the user's current editing context. Design stance chosen by the user (2026-09-20, Detached Task): a **non-activating floating tray** (`Qt::Tool` + `WA_ShowWithoutActivating`, auto-appears on task submission, folds away when everything finishes) rather than a resident docked panel; commands that would switch the composition or playback state are **rejected with a reason** rather than executed and then undone/restored; and writes are **deferred/queued** while the user is mid-interaction (viewport drag, gizmo, timeline drag, modal dialog) instead of interrupting the undo/gizmo boundary. Generalizable: keep view, selection, and focus untouched, and surface status without stealing focus. Confidence: 0.6
- Approval gates inside background/detached execution must stay non-modal: park the task in an explicit pre-execution "AwaitingApproval" state and resolve it with approve/deny controls inside the task tray, never by popping the existing modal `QMessageBox` approval dialog — a modal steals focus and is treated as breaking the "don't interrupt the user's work" premise. Corollaries chosen by the user (2026-09-20, Detached Task approval design): harmless read-only operations (get_*/list_*) auto-execute even under an AskEveryTime setting, high-risk deletions route their `userConfirmed` flag through the tray approval, a pending approval keeps the tray expanded (an approval must never be hidden by the fold-away behavior), and existing approval settings (the `toolApprovalMode` QSettings key) are reused rather than duplicated. Confidence: 0.55
- Never let a mockup or implementation fill an unknown value with a flattering default: when a status is not computed (e.g. project health), display 「Unknown」/「Not checked」 rather than guessing 「Healthy」. When designing a preview/status surface, the mock may show a Healthy example, but the implementation must resolve the real data owner and trigger first, and those unresolved data paths are called out as 未確認 before code is written. Applied 2026-09-26 (project-open picker v2: project thumbnail owner in `ArtifactProjectService` unconfirmed, health computation trigger unconfirmed, D3D12/Vulkan preview acquisition unconfirmed). Confidence: 0.55
- Treats silent no-ops as defects: an operation that skips work (missing active composition, a Start press while a render is already running, an empty range) must surface a user-visible message (dialog / log line) instead of returning silently, and long-running background work must report progress and state so the user can tell whether it even started. Triggered 2026-09-22 by a render-queue defect report (「エラーが多い」「レンダリングが始まってるのかさえ不明だ　ゲージ更新もなし」), which led to wiring the UI to the service's shared global EventBus, adding dialogs/log notices to previously silent early-returns, and making frame logs visible by default. Confidence: 0.55
- An enum/list that a feature never reaches is worse than a missing feature, because the entry's whole reason for existing (limiting the effect to a region, keeping the layer off the backdrop, excluding a path from the fast route) is silently discarded. A UI affordance naming the specific excluded case is the tell: 「Add a blur adjustment layer」 sitting in the menu while the effect planner refuses adjustment layers outright means the most advertised adjustment-layer workflow does nothing. The audit question is therefore not 「is this effect implemented」 but 「which FEATURE GATE silently switches this layer's contribution off」, and a gate that also voids opacity/transform (typically by forcing them to 1.0/identity) is a compound defect reported as one. Confidence: 0.5
- A binding that shows up in the settings UI is a promise of behavior, not a label: a shortcut row reading 「Ctrl+F 検索」 that does nothing when pressed is treated as a shipped defect, so a missing handler triggers building the whole feature (the Find/Replace bar) rather than un-assigning the key or hiding the row. Corollary: after registering a batch of conventional editor keys, sweep for registered-but-unwired IDs before declaring the batch done. Confidence: 0.55
- Editor features are expected to match what every other editor does without being told: seed the find field from the current selection, show an 「N of M」 match count, make Enter advance to the next match, make Escape return focus to the editor, have Replace All replace every occurrence, and skip the line-number/decorations when the user has a real selection so the highlight does not tint the selected region. QTextEdit's built-in find bar is not acceptable — the in-house one is styled and context-consistent. Confidence: 0.55
- A visual effect gets exactly one drawing path, chosen for correctness rather than convenience: the current-line band lives in the `ExtraSelection` list (as a `FullWidthSelection`) rather than a `paintEvent` override specifically so a later pass sharing that same list (the error underline) cannot overwrite it — which is only possible because the two share one mechanism. Painting it in both places double-applied the alpha. Confidence: 0.5
- When several draggable handles can fall inside one hit threshold, a FIXED priority order is the wrong resolution — it makes one handle permanently ungrabbable whenever a neighbour is near. Resolve toward the cursor instead: compute each candidate's handle position, take the one whose distance to the pointer is smallest within the threshold, and let the listed order break an exact tie. The check that keeps this from becoming a false alarm is comparing the DRAW placement formula against the HIT formula: when both use the same expression (here `offset` is drawn and hit at `(start + end) * 0.5 + offset`), the handles separate in the default state, so the defect is the order-dependence, not a proven overlap — worth fixing, but not worth shipping as 「start ハンドル掴めない」. Applied 2026-09-27 (text range selectors, vertical and horizontal, replaced three near-identical priority chains with one proximity helper). Confidence: 0.55
- A number in a diagnostic badge is a claim about COVERAGE, so it must say when the number is not exhaustive. Established 2026-09-29: when the unreadable-frame check was reduced from all 1000 frames to a 3-frame sample (first / middle / last), the label read `Unreadable: %1` and was changed to `Unreadable: %1 sampled` — without the suffix the badge says 「2 frames are unreadable」 when it means 「2 of the 3 sampled frames were」, which is the same lying-UI class as a default that answers 「I don't know」 with a confident wrong value. Generalize: when a pass changes a diagnostic's METHOD (exhaustive → sampled, incremental → periodic, recomputed → cached, on-demand → lazily deferred), grep the badge / tooltip / toast strings that render its count and update the TEXT in the same pass as the logic — a stale method label is invisible to any review that only reads the loop. Related: a badge whose wording is itself a spec item still has to be truthful about how its number is produced, and 「サンプル基準」 belongs in the label the user reads, not only in a code comment. Confidence: 0.55
- An AUTOMATION that removes work from the user's review queue must leave a visible trace of what it decided, and the trace must EXCLUDE the trivial cases or its count is noise. Established 2026-10-01 while adding automatic conflict resolution to the snapshot merge: a heuristic that settles a path without asking makes that path VANISH from the conflict list, so an edit can appear to have been dropped. The landed shape is a separate `autoResolved` list of `(path, reason)` on the result struct, threaded as an out-parameter through the merge helpers, with the status line carrying the count (`(%1 auto-resolved)`) so the user can see that something was decided on their behalf. The exclusion rule is the part that makes the number usable: the ordinary reasons — 「ours-only」, 「theirs-only」, 「identical」 — are recorded as NOT auto-resolved, because recording them would put 「12 auto-resolved」 on every merge where one side simply edited a file and would train the user to ignore the badge. Only the surprising rules (numeric-tolerance, same-direction, string-ignoring-space) are worth explaining. This is the same class as the sampled-badge rule above and as the 「default answers ‘I don't know’ with a confident wrong value」 defect: a UI that hides a decision is lying by omission even when the decision was correct. Corollary for the design doc: the set of cases deliberately NOT automated is as much a deliverable as the rules that are, and each one carries its reason (different strings → guessing is silent data loss; one side blanked → 「reset to default」 and 「mid-edit」 are indistinguishable; a bool flipped both ways has no majority rule), because the next session will otherwise read the omission as an oversight. Confidence: 0.55
- A new manipulator needs a SELECTION concept, and when the app has no UI for the coarser selection the coarse target should be DERIVED from the finest selection that does exist — not a new selection UI invented in the same pass. Applied 2026-10-05 (mask bounding-box gizmo): the viewport had vertex-level selection (a vector of `MaskVertexAddress`) and NO mask-level selection at all — no 「which mask is active」 state, no mask picker — so the gizmo's target was computed in the overlay draw as 「the mask index shared by EVERY selected vertex, and only when all of them agree」 (`std::all_of` over the address tuple's first element), with the member's doc comment stating that `-1` means the gizmo is off and that this derivation is the ONLY entry point until a mask-selection UI exists. Two rules. (1) Derive the coarse target and make the AMBIGUITY rule explicit — 「selected vertices spanning two masks → no gizmo」 is a deliberate documented behaviour, while last-writer-wins makes the gizmo jump between masks as the selection changes. (2) The derivation must be a NAMED single-place computation with the limitation in its comment, because the gizmo's press path, hover path and draw path all consume that value and three independent recomputations would drift. The user-visible consequence belongs in the report as a 未確認 line, not only in a member comment. Confidence: 0.5
- A destructive key (Delete / Backspace) pressed on a row that represents a CHILD of the currently selected item must delete the CHILD, and the ownership decision must be FAIL-CLOSED: once the pressed row's identity is resolvable, no downstream failure may escalate the action to the parent. Applied 2026-10-06 (timeline left pane, Text Animator): the user stated the requirement as a FAMILY rule — 「タイムライン左ペインで削除可能な要素は選択して削除できるようにしたい」 — so the delivered fix is a generic dispatcher, not an animator-only branch. The root cause was a handler chain in which 「この行は私の担当でない」 and 「私は失敗した」 shared one `false` return value: `keyPressEvent` tried `deleteSelectedMask()` (which reads only `selectedMaskLayerId` + an integer index, so it is always false for an animator) and fell through to layer deletion. The shipped shape resolves the row's identity FIRST (a parse helper turning `text.animators.<index>` into an index) and then returns true for every later failure mode — layer lookup failed, cast failed, undo push failed — with a comment stating that the key's owner is the animator row and the parent must not be destroyed. So the deliverable is not just the delete path: the child row must also CARRY that identity (an always-empty `propertyPath` is why 「which component is selected」 had no state at all), clicking it must set selection, and the paint path must show a highlight, or the user cannot see what a subsequent Delete will remove. Confidence: 0.6
