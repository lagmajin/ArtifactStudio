# Keying Effects R&D

**最終更新:** 2026-10-27

## Scope and method

Reviewed the keying Core API and implementation, Artifact keying wrappers and GPU shader, effect registration and composition restoration, and the property editor's path handling. Compared the exposed controls and workflow with public Foundry Nuke and Adobe After Effects documentation. This is a code-path audit; no visual quality or performance benchmark was run.

## Current implementation evidence

- A pre-existing `ArtifactCoreKeyingVideoInputTest` covers one synthetic video-input path: it writes a three-frame MJPG AVI, decodes it, invokes Core Chroma Key, composites over blue, and checks screen/subject pixels. It is registered with `ARTIFACT_ENABLE_KEYING_VIDEO_TEST` (or the broad test suite); it does not exercise Artifact effect wrappers, IBK, GPU rendering, the application's video-layer decoder, real-time playback, or audio synchronization. It requires the selected OpenCV videoio backend to support MJPG writing and reading; `writer.isOpened()` is an assertion, so a missing codec/backend fails the test rather than skipping it.
- The Core video test asserts that three frames were decoded and keyed, but it does not prove frame order or motion: the synthetic subject moves one pixel per frame while the foreground assertion samples inside a 36-pixel-wide rectangle, so a repeated or reordered frame could still satisfy that sample. It also does not inspect edge pixels, temporal stability, or decoded frame timestamps.
- The current worktree contains an additional 39-case `ArtifactKeyingEffectContractTest`, selectable with `ARTIFACT_ENABLE_KEYING_EFFECT_TEST`. Its direct pixel-algorithm coverage primarily calls Core `processChromaKey`, `processLumaKey`, `processDifferenceKey`, and `processIBK`; separate cases instantiate Artifact effects and call `applyCPUOnly` to verify wrapper behavior. Two cases whose names mention GPU test parameter conversion/radius policy, and another checks construction of a GPU spatial node; they do not create a GPU device, dispatch a shader, or compare rendered pixels. The suite also uses a bundled still image, so it is not a video decode or playback test.
- Two Artifact cases require `ARTIFACT_KEYING_REAL_FIXTURE`; the CTest property supplies the bundled JPEG path, and the real-footage Chroma case additionally enforces its SHA-256 and 540×960 dimensions. Missing fixture configuration or a changed asset fails by assertion rather than skipping, so direct executable invocation must provide the same environment variable.
- The real-footage Chroma assertion samples four fixed coordinates only (backing, jacket, wall, and a hair-edge pixel); it is a point-sample smoke/contract check, not a full-frame matte metric, reference-image comparison, or broad visual-quality acceptance.
- There are three relevant CTest targets in the current worktree: the dedicated Core video-input target, the dedicated 39-case Artifact keying contract target, and `ArtifactProjectRoundTripTest`, which includes two IBK persistence cases. Only the first two have keying-specific standalone options; the project round-trip target is registered under `ARTIFACT_BUILD_TESTS`.
- The two IBK persistence cases are GTest cases inside a 10-case `ArtifactProjectRoundTripTest` executable, registered as one CTest test by the shared `artifact_add_test` helper. Selecting that CTest target runs the whole executable; isolating only the IBK cases requires a GTest filter at executable invocation.
- Static CMake registration audit: both keying options enter the test configuration and the standalone targets are behind the expected flags. If GTest is absent, however, `ARTIFACT_ENABLE_KEYING_EFFECT_TEST` is in the explicit fatal-error list, while `ARTIFACT_ENABLE_KEYING_VIDEO_TEST` is not; the latter can fall through to the generic warning that GTest tests are skipped, leaving the requested video target absent. Also, a standalone test flag does not make configuration test-only: the root CMake unconditionally adds ArtifactCore and Artifact, and ArtifactCore unconditionally requires OpenCV. These are source-level findings only; configure was not run.
- Final source-tree search found exactly two keying-named test source files under `tests/`: the tracked Core video test and the current-worktree Artifact contract test. The two IBK project-persistence cases live inside the broader project round-trip source, rather than a third keying-specific source file. The effect-contract source, fixture, CMake registration, and project-round-trip additions are uncommitted current-worktree changes; the Core video source and its registration are in the tracked baseline.
- Core provides Chroma, Luma, Difference, and IBK processing. IBK also exposes temporal-median clean-plate generation.
- Repository search found no production caller for `autoGenerateCleanPlate` outside its Core declaration/definition; the contract test exercises the algorithm directly, but there is no verified Artifact UI or frame-selection workflow invoking it.
- `autoGenerateCleanPlate` validates each frame's dimensions, data pointer, and channel order, but does not inspect `alphaMode`; it computes an independent median for all four stored channels and the default output descriptor retains an unknown alpha mode. Current fixtures mostly use opaque samples, so behavior for semi-transparent or premultiplied frames is unspecified and untested. Define an input/output alpha contract before integrating frame-based generation into a user workflow.
- Artifact wraps IBK for CPU and GPU processing. The effect is registered as `Effect.Keying.IBKKeyer`, restored from composition data, and exposes parameters, preview mode, and a clean-plate path.
- Single IBK layer-effect restore is covered, but duplicate-ID variants are not. `ArtifactEffectService::createEffect` accepts `ibk_keyer` / `Effect.Keying.IBKKeyer`, while `availableEffects()` does not list either ID. Layer insertion uses numeric IDs such as `-2`; the restore normalizer strips a numeric suffix only when the base ID appears in that catalog. Effect copies use `__copy` / `__copy2`, and the restore normalizer does not strip that form. Since IBK's base IDs are absent from the catalog, a second or copied IBK ID is passed to the factory as-is and is not handled by the IBK factory branch; the restore loop then skips it if creation fails. This is a static code-path finding; neither duplicate form has a round-trip contract case or runtime verification.
- Clean-plate path selection was previously rendered as a generic string field because `cleanPlatePath` was missing from the path-property recognizer. It now uses the existing image-path editor and image file filter.
- An empty `cleanPlatePath` previously failed validation and left the prior in-memory plate active. Empty input now clears the plate, and a contract case checks that the effect passes the source through after clearing.
- Composition serialization stores string properties, including `cleanPlatePath`, as the path value and restores them through `setPropertyValue`. Static inspection of `ArtifactProjectStatistics::collectMetadata` and `ProjectMetadataValueCollector` shows that packaging collects project Footage `filePath` values and selected layer-JSON paths ending in `sourcePath`, `filePath`, `fontPath`, or `fontFile`; `cleanPlatePath` is not among them. `ArtifactProjectPackager` copies only those collected external files and rewrites JSON keys named `filePath`, so an IBK clean plate is not included or relativized by the current package path. This is a static code-path finding, not a package-runtime test. A missing or size-mismatched plate currently makes the IBK wrapper pass the source through. `ArtifactProjectRoundTripTest.CompositionIBKPropertiesSurviveProjectReload` exercises composition serialization, restored effect type/ID, numeric controls, preview mode, and the loadable clean-plate path, then applies the reloaded effect to the matching fixture and checks its matte output. `EditedEffectStackOrderAndSettingsSurviveReload` covers one IBK in a layer effect stack, its order, type, numeric control, and clean-plate path. Neither case covers duplicate/copy IDs or project packaging/relinking; an absolute fixture path can remain loadable without proving asset portability. Both cases are part of `ArtifactProjectRoundTripTest`, which is guarded by `ARTIFACT_BUILD_TESTS`; the separate 39-case keying contract suite is selectable with `ARTIFACT_ENABLE_KEYING_EFFECT_TEST`. None has been built or executed in this pass.
- IBK CPU morphology accepts radii 0–64. The HLSL shader samples at most radius 8 (a fixed 17×17 window). Values 9–64 could therefore produce different CPU and GPU results. The Artifact GPU wrapper now routes such values to the CPU implementation, preserving the existing CPU range. Core exposes the shader radius limit as a shared predicate; the contract test checks that predicate at supported and unsupported values and checks packed radii, but does not execute the Artifact wrapper's GPU branch or prove that it actually takes the CPU fallback.
- Chroma Key's Core buffer contract previously carried channel order but not alpha mode. CPU keyed stored RGB directly while HLSL always unpremultiplied RGB and always premultiplied output. This disagreed for straight inputs with partial alpha and for premultiplied inputs on CPU. The buffer now carries `SurfaceAlphaMode`; CPU and GPU paths interpret premultiplied pixels in straight color space and write back in the matching convention. A Core contract case compares equivalent straight/premultiplied samples and checks the GPU parameter flag. Runtime CPU/GPU parity remains unverified. Opaque-tagged source images are treated as straight RGB. After effect processing, `ArtifactAbstractEffect::applyConfigured` restores any fully specified source descriptor, so an Opaque-tagged source remains labeled Opaque even when keying writes fractional alpha. This is a confirmed metadata/content mismatch; correcting it requires an explicit effect output alpha-mode contract and runtime acceptance.
- Luma and Difference Key had the same partial-alpha class of defect: they evaluated stored premultiplied RGB directly and reduced alpha without reducing premultiplied color. Their Core buffer contracts now carry alpha mode; CPU and standalone GPU paths evaluate unassociated color and multiply premultiplied output color by the matte. Their composition-resident shader bodies now also unassociate the linear-premultiplied resident surface for key evaluation and write premultiplied results. Core and Artifact-wrapper contract cases compare equivalent half-alpha straight/premultiplied samples. GPU execution parity still needs acceptance.
- The two Luma/Difference GPU paths have different explicit input contracts: standalone shaders branch on `SourcePremultiplied` and preserve straight RGB storage for straight-tagged inputs, while Composition resident shaders always unassociate and reassociate because their resident surface is linear-premultiplied. Their formulas statically match the CPU branches, but the contract suite does not execute either GPU path; pixel parity is still runtime-unverified.
- A separate legacy `ArtifactCore::LumaKey::process` API remains in `ArtifactCore/src/ImageProcessing/LumaKey.cpp`; repository search found no production call sites outside its own implementation/declaration. Its `ImageF32x4_RGBA` overload routes to a raw `float4` path that applies legacy channel weights (`x * 0.114`, `y * 0.587`, `z * 0.299`) and changes alpha without associating RGB for premultiplied images. This differs from the active `ArtifactCore::Keying::processLumaKey` contract. It is currently a dormant public API; determine whether to remove/deprecate it or add an explicit compatibility contract before routing callers to it.
- `IBKKeyerEffect` selects `ComputeMode::AUTO`. The ordinary Composition view, Preview, and Render Controller call `applyToCpuSurface`; because IBK supports CPU, this route forces CPU. `ArtifactAbstractEffect::apply()` would select the GPU implementation under AUTO, but a repository search found no production caller for it; the DAG executor and `EffectHostContract` routes also have no instantiation outside their definitions and the graph visualization builds nodes only to display them. Therefore the GPU performance issue is currently a latent risk, not an established playback bottleneck. If invoked, the GPU wrapper allocates input/output textures, a parameter buffer, a compute pipeline, and a staging texture per call, then performs `Flush()` and `WaitForIdle()` to read the result back to CPU. A future production GPU route needs profiling and GPU-resident downstream processing before claiming playback suitability.
- IBK's public Artifact setters clamp to the displayed hard ranges, and `IBKGpuParams::fromParams` sanitizes non-finite values and clamps its packed values. The Core CPU `processIBK` path independently sanitizes non-finite controls but does not apply the same upper bounds for `screenCorrection`, `edgeMatteSoftness`, and `garbageMatteGamma`; e.g. a direct Core call with `screenCorrection=9` uses 9 on CPU while GPU packing uses 4. Normal Artifact property edits are clamped before reaching Core, so this mismatch is exposed to direct Core callers and future API integrations. No CPU/GPU execution comparison has been run.
- IBK's Core input validation checks pointers, dimensions, and channel orders, but does not sanitize foreground or clean-plate pixel samples. In particular, a non-finite clean-plate RGB sample reaches `distance`, then the matte and output alpha; a non-finite foreground alpha also reaches output alpha. The temporal clean-plate generator replaces non-finite samples with zero, but callers can still supply a malformed image directly or load non-finite float image data. Current contracts cover non-finite temporal-generation samples and control values, not non-finite `processIBK` pixels. Define whether processing should reject invalid pixels or sanitize them, then assert finite deterministic output (or unchanged output on rejection) on both CPU and GPU paths.
- A repository-wide search found no reference to `ArtifactCore/include/ImageProcessing/DirectCompute/IBKKeyer.hlsl`. Its morphology loop combines erosion and dilation updates into one traversal of the unmodified matte; that is not equivalent in general to the sequential erode-then-dilate passes in Core CPU and the embedded Artifact GPU shader. Treat this standalone shader as unverified/dormant and reconcile or remove it before registering it as an execution path.
- The current worktree contains an additional `ArtifactKeyingEffectContractTest` source with 39 cases. It covers synthetic Core Chroma, Luma, Difference, and IBK behavior; Artifact-wrapper propagation and diagnostic views; Chroma resident-node parameter packing; a real green-screen still with background, foreground, and soft hair-edge samples; temporal-median clean-plate generation; the GPU morphology-support predicate and parameter packing; IBK property range/clamp parity and foreground-alpha clamping; loading an IBK clean plate from the configured JPEG path; and preservation of the prior plate when a replacement path is invalid. The test source and VOA JPEG fixture are currently untracked, and their target registration/fixture wiring are uncommitted diffs; they are not part of the tracked repository baseline yet. The suite overlaps the tracked video-input case only on basic Core Chroma/matte behavior; it does not repeat video encode/decode coverage. The project round-trip suite separately contains composition- and layer-level IBK persistence coverage in a modified tracked test file. These current-worktree contracts do not catch the Artifact Chroma wrapper's advertised despill mode 3 being clamped to 2 by its typed setter, and there is no assertion for IBK preview mode 2's premultiplied-RGB display formula. Neither keying suite establishes IBK quality on uneven backing, fine hair, translucent detail, or GPU/CPU image parity, and neither has been executed in this pass.
- In the current worktree diff, the Artifact contract target is registered as `ArtifactKeyingEffectContractTest` behind `ARTIFACT_BUILD_TESTS` or the standalone `ARTIFACT_ENABLE_KEYING_EFFECT_TEST` option. Its registration sits outside the broader color/effect test block, so the keying option does not register that block's unrelated contract targets. The option does not make the overall project configure/build keying-only: the root project still adds its normal application and module targets, and `ARTIFACT_BUILD_TESTS` also registers the broad test suite. The separate, tracked synthetic video-input test uses `ARTIFACT_ENABLE_KEYING_VIDEO_TEST` and is registered in the ArtifactCore test subdirectory; enabling only the effect option does not select it. Root CMake adds `tests/Artifact` for the effect option and requires GTest. CTest supplies the VOA fixture path through `ARTIFACT_KEYING_REAL_FIXTURE`; the real-still and clean-plate cases load it through `ImageF32x4_RGBA::load`, which tries OpenImageIO first and falls back to QImage, without a direct OpenCV test dependency. The target is labeled CPU/contract. After configuring, the target can be built as `ArtifactKeyingEffectContractTest` and selected with `ctest --test-dir <build-dir> --output-on-failure -R '^ArtifactKeyingEffectContractTest$'`. These commands are documented but have not been run.
- GPU-named cases in the current 39-case worktree suite do not dispatch a shader: `ChromaGpuParameterConversionSanitizesInvalidValues` and the IBK GPU cases assert CPU-side parameter packing/radius policy, while `ChromaKeyMapsPropertiesToResidentGpuNodeParameters` inspects a CPU-built node and its parameter slots. None creates a graphics device, executes a compute/raster shader, or compares GPU output pixels to CPU output. GPU behavior is therefore statically inspected only; runtime rendering parity remains unverified.
- The bundled JPEG is 540 × 960 and its SHA-256 matches the fixture README; the Chroma real-footage test now verifies that hash before checking fixed sample coordinates. An earlier OpenCV-based offline pixel/formula inspection estimated alpha `0.0303`, `1.0`, and `1.0` at the backing, jacket, and wall sample coordinates. A Pillow scan of the JPEG estimates alpha around `0.34` at the added hair-edge point `(369, 282)`. These independent-decoder calculations help choose tolerant assertions but do not establish the production loader's decoded values or substitute for running the effect test.
- The Commons source page gives the original video as 1,080 × 1,920 and 14.268 seconds, with VOA Learning English attribution, but also carries a license-review-needed marker. VOA's official terms make exclusively VOA-produced material public domain while excluding third-party licensed content. The fixture README now records that caveat and the fact that the original extraction tool/version was not retained; the bundled raster is hash-pinned.
- The real-footage Chroma and IBK tests now decode the same JPEG with the application's `ImageF32x4_RGBA::load` path. That method tries OpenImageIO and falls back to QImage; the Core image type stores canonical BGRA backing while `getPixel(x, y)` exposes logical RGBA. Using the production loader avoids a separate OpenCV decoder/conversion path in these wrapper checks.
- The Chroma contract cases compare logical pixels supplied in RGBA and BGRA order, alongside straight/premultiplied alpha coverage. Luma and Difference now also have a shared contract case comparing two logical pixels across RGBA and BGRA ingress, including channel-swapped output equality.
- All four Core keyers now share explicit rejection coverage for missing buffers and zero/negative dimensions; each rejected call also checks that the destination remains untouched.
- IBK now also has explicit rejection coverage for an unknown foreground or clean-plate channel order, including an unchanged-output assertion; valid RGBA/BGRA combinations remain covered separately.
- Chroma, Luma, and Difference document that source and destination buffers must be distinct, and tests reject exact pointer aliasing. Their raw-pointer contracts do not expose allocation lengths, and the implementations only compare pointer equality; partial overlap is not detected and can race with tiled reads/writes. Such inputs remain outside the documented contract and are intentionally not exercised by the tests.
- Chroma, Luma, and Difference now share a Core contract case that checks Matte view against the Final matte: RGB must equal the final alpha and preview alpha must be opaque. It also checks Chroma's Despill RGB and Status-map channel formulas. A separate Artifact-wrapper case sets each public `viewMode` property and checks the CPU result against Final alpha.
- Parameter-boundary cases now cover Chroma GPU-parameter finite fallback, channel/clip clamps and invalid-mode normalization; Luma reversed threshold ordering and view-mode clamping; and Difference non-finite/out-of-range parameter equivalence to explicit finite defaults.
- A Chroma wrapper contract now maps its public settings into all 15 Composition resident node parameter slots and checks the spatial-domain gate when choke is enabled; this validates node construction without dispatching a GPU shader. Static inspection found the Composition renderer reads slots 0–14 into the corresponding `ChromaKeyParams` fields in the same order; that consumer mapping is not runtime-tested by this CPU suite.
- A Core case now exercises Target Neutral (mode 3) and distinguishes it from Luminance Preserve. Chroma's Despill Mode property advertises/selects values 0–3 and Core/GPU parameter normalization accepts 0–3, but `ChromaKeyEffectCPUImpl::setDespillMode` clamps to 0–2. Thus public value 3 cannot reach the Artifact effect through its typed setter. This wrapper/Core range mismatch remains unresolved.
- A shared Core contract case now feeds Chroma, Luma, and Difference Key premultiplied pixels with zero alpha, non-finite RGB, and non-finite alpha. It asserts transparent output and finite channels, guarding against divide-by-zero and NaN propagation.
- IBK's Artifact wrapper passes through the source when the clean plate is missing or has mismatched dimensions. A wrapper case now checks exact pixel pass-through for a dimension mismatch. The Core `IBKBuffers` contract has no alpha-mode field; CPU and GPU processing both use foreground RGB directly and multiply keyed color by the new alpha. The Artifact wrapper preserves the source descriptor. This means premultiplied inputs are interpreted as straight RGB, while straight-tagged inputs receive premultiplied RGB under a straight descriptor. IBK currently lacks an equivalent straight/premultiplied input contract case, and this convention mismatch needs a scoped implementation fix before alpha parity can be considered complete.
- A Core contract now exercises all four RGBA/BGRA foreground and clean-plate order combinations, normalizes outputs back to logical RGB, and checks channel-order parity plus transparent-background/opaque-foreground alpha behavior.
- IBK's Matte preview (mode 1) converts the keyed alpha to opaque grayscale; an Artifact-wrapper contract case now compares its channels against Final-mode alpha. Preview mode 2 is labeled "Premultiplied RGB", but `processIBK` already multiplies output RGB by the keyed alpha and `applyIBKPreview` multiplies those channels by alpha again before setting alpha to 1. This appears to double-apply alpha and needs a decision about the intended preview display before changing it.
- Clean-plate temporal-median coverage now includes odd and even frame counts (the even case averages the middle pair), normalization from RGBA and BGRA ingress into canonical BGRA backing, output channel-order verification, and replacement of non-finite samples with zero. Empty input and mismatched frame dimensions are rejected while preserving the caller's pre-existing output image. The explicit 4096-frame acceptance boundary and 4097-frame rejection are also covered, including preservation of the existing output on rejection.
- A separate Core test synthesizes a short MJPEG green-screen clip, decodes all frames, keys them, and composites over blue. The Artifact contract test uses a bundled VOA frame and checks backing removal plus two foreground regions. Neither test is a GPU parity or broad visual-quality acceptance suite.
- CPU Chroma Light Wrap previously sampled neighboring colors from the same output buffer that parallel workers were changing. The result could depend on pixel scheduling and differed from the GPU shader, which samples the immutable input texture. CPU Light Wrap now samples the original source and converts premultiplied neighbors to straight color before blending, matching the GPU source domain and removing that read/write race. Runtime parity remains unverified.

## Donor findings

- Foundry's IBK workflow uses a clean plate containing background color variation, which is why it can handle uneven blue/green screens. It distinguishes the clean-plate construction step from pulling the foreground key. [Foundry IBKGizmo documentation](https://learn.foundry.com/nuke/15.1v1/content/reference_guide/keyer_nodes/ibkgizmo.html)
- Foundry Keylight exposes separate screen matte, inside/holdout, and outside/garbage mattes, plus screen color, alpha/despill bias, clip controls, and diagnostic views. Its documentation cautions that aggressive clipping can harden or destroy edges. [Foundry Keylight documentation](https://learn.foundry.com/nuke/17.1/content/reference_guide/keyer_nodes/keylight.html)
- Adobe documents keying as a refinement chain: inspect the matte, clean edges, and apply spill suppression when needed. Its Key Cleaner and Advanced Spill Suppressor guidance makes these explicit stages rather than assuming a single key operation solves all footage. [Adobe keying effects](https://helpx.adobe.com/after-effects/desktop/animate-in-after-effects/work-with-keying-effects/keying-effects.html)
- Blender's Keying node exposes a matte output, an edge-detection output, optional core and garbage mattes, and separate pre/post processing and despill controls. This makes diagnostic visibility and masks part of the node contract. [Blender Keying Node documentation](https://docs.blender.org/manual/en/4.5/compositing/types/keying/keying.html)
- Blackmagic's Resolve 20 VFX guide recommends separating spill suppression into another branch when that gives more control over the matte and color correction; its workflow combines core, edge, and window keys where a single key is insufficient. This is evidence for staged workflows, not a requirement to duplicate that node graph. [DaVinci Resolve 20 Advanced Visual Effects guide](https://documents.blackmagicdesign.com/UserManuals/DaVinci-Resolve-20-Advanced-Visual-Effects.pdf)

These are workflow references, not claims that the donor algorithms or proprietary implementation details should be copied.

## R&D conclusions and next acceptance work

1. Keep the newly added CPU fallback for unsupported GPU morphology radii; it avoids silently changing a saved 9–64 radius setting.
2. Validate the clean-plate picker with actual image formats used by the image loader and verify path persistence across save/reopen.
3. Verify whether clean-plate paths participate in project packaging/relinking; define a user-visible missing/mismatched plate state before relying on external absolute paths.
4. Add an IBK real-footage acceptance set with a matched clean plate, uneven screen illumination, hair/soft edges, and a holdout region. Record representative foreground/background alpha samples and compare against a baseline image; do not rely on a single aggregate score.
5. Compare Chroma, Luma, Difference, and IBK CPU/GPU output pixelwise on the same synthetic and real-footage inputs. Include BGRA/RGBA, straight/premultiplied alpha, diagnostics, and supported IBK morphology radii 0 and 8; confirm GPU requests above 8 take the CPU fallback.
6. Verify Chroma Key output alpha metadata for Opaque-tagged sources; pixels with keyed alpha must not remain advertised as Opaque.
7. First identify and document the intended production caller for `apply()`/DAG evaluation. If IBK is moved to that route, profile it in a representative composition and preserve GPU residency downstream instead of creating resources and synchronously reading back each frame.
8. Consider later exposing independent holdout/garbage matte inputs and diagnostic matte views, but first define their property ownership, persistence, and UI surface. The current generic property list is not a substitute for a complete keying workflow.
9. Chroma Key already offers matte/diagnostic modes, but Artifact's generic effect masks blend the finished effect back against its source; they do not modify the keyer's alpha matte. They are therefore not equivalent to a garbage/core matte input. If IBK adds those inputs, define a keyer-specific matte contract instead of treating the generic effect mask as a substitute.
10. Run `ArtifactProjectRoundTripTest` through `ARTIFACT_BUILD_TESTS` to verify production project save/reopen. Separately verify clean-plate packaging/relink behavior for moved projects and missing source files; the round-trip case only verifies a loadable absolute fixture path.
11. Add layer round-trip coverage for both a second IBK (`Effect.Keying.IBKKeyer-2`) and the effect-copy ID (`Effect.Keying.IBKKeyer__copy`): after save/reload, assert that each entry remains an `IBKKeyerEffect`, keeps its distinct ID, and restores its independent settings. Register the IBK base IDs in `availableEffects()` so numeric suffix normalization can resolve them, and explicitly extend/test the restore normalizer for `__copy` / `__copyN`; catalog registration alone does not handle copy IDs. The implementation and test changes are in the Artifact child repository and require explicit authorization under the repository instructions.
12. Run the standalone Artifact keying contract test, including Chroma channel-order/edge-finishing cases and Luma/Difference Core plus Artifact-wrapper straight/premultiplied cases. It has not been built or executed.
13. Align the Core CPU IBK parameter bounds with `IBKGpuParams::fromParams`, or explicitly document the intentional API distinction; add a direct Core contract covering upper bounds and non-finite controls before relying on CPU/GPU parity for arbitrary Core inputs.
14. Confirm whether the unreferenced standalone IBK HLSL is intended to be maintained; if it is, align its morphology pass ordering with Core CPU and the embedded GPU shader, then add execution-level parity coverage.
15. Define IBK behavior for non-finite foreground/clean-plate pixel channels and alpha, then add Core and GPU contracts that verify finite output or a documented rejection path.
