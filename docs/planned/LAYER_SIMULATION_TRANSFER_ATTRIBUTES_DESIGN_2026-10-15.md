# レイヤー粒子化・シミュレーション間接続・属性設計メモ

**最終更新:** 2026-10-15
**状態:** 独立コアの初期実装あり（実アプリ未接続・コンパイル／実行未検証）

## 実アプリから隔離して育てる方針

- `ArtifactCore/include/Simulation/MaterialTransfer.hpp` をopt-inの通常ヘッダーとして追加。既存module、ソルバー、UI、CMakeから参照せず、既存の公開データ構造と保存形式を変更しない。
- 初期実装は型付き標準属性と1対1の受け渡し準備。Convertは元を消費する変換、SpawnSecondaryは別途予算を与えた派生生成。質量・体積・速度を保持し、暗黙の単位／座標変換を行わない。
- 呼び出し側所有の`std::span`を使い、所有コンテナ・ヒープ確保は追加しない。入力全体を検証してから出力し、容量不足はDeferとして出力を変更しない。
- prepareはソルバーを変更しない。変換元の消費は、受け取り側が全件commitした後にのみ行う。ソルバー間transactionは未実装で、呼び出し側契約をコメントに明記した。
- `MaterialAttributes.hpp` に所属・単位・数値キー付きの借用型付き属性列を追加。float／uint64／Vector3を扱い、列長とキー重複を検査する。lookupの欠損／型不一致は明示的にnullを返す。1列の転送と欠損時の既定値は後述のinheritAttributeで実装。補間とGPU ABIは未実装。呼び出し側が寿命と評価中の不変性を保証する。
- `MaterialTransferLedger.hpp` に固定容量の処理済みbatch記録とcheckpoint view／restoreを追加。connection／occurrence／tickで重複を判別し、満杯ならDefer、無効な復元なら現状態を維持する。単一所有者限定であり、ソルバーcommitとの原子性やディスク永続化を保証しない。checkpoint viewは借用であり、後から復元するには呼び出し側で保存する。ソルバー状態と台帳を同じ時点へ復元する必要がある。
- `tests/ArtifactCore/MaterialTransferStandaloneTest.cpp` に容量不足、全件検証、座標不一致、属性保持、変換と派生、空入力の確認コードを追加。ビルド登録・実行は行っていない。
- 次段階は属性転送／継承規則、発生IDの払い出し、変換commitの原子性、破砕→粉じんadapter。現時点では実ソルバー間接続の完成を意味しない。
- 2026-10-15: ユーザー指定によりコンパイル／テストを実行せず静的確認までとする。検証コードには属性型／列長／重複、台帳容量／重複／復元失敗の確認も追加したが、動作確認済みとは扱わない。
- `MaterialDissolve.hpp` にサンプルごとの絶対release tickと、半開区間(previousTick, currentTick]で発生対象を抽出する処理を追加。元の可視判定にも同じrelease tickを使う。区間内の全件が出力容量に収まらなければ書き込まずDeferとする。容量不足で時計だけを先へ進めず、同じ区間を再試行する。可視状態の公開はspawn commit後とし、逆seekは状態復元／replay側で扱う。
- 通常のprepareとdissolve入力は安定IDの厳密昇順を要求し、ID重複を線形走査で拒否する。並べ替えは呼び出し側のコールドパス責務。派生粒子を同一発生元から複数作る場合は、別途子ID／親ID契約を設計する必要がある。
- dissolveのSpawn.tickは実際のrelease tickであり、台帳のbatch tickはrequest.tick。区間を飛び越えて評価するadapterは、誕生後の経過時間をソルバーへ明示して追従させる必要がある。画像のサンプリング、GPU消失マスク、方向／noiseからrelease tickを構築する処理はまだ含まない。
- `inheritAttribute<T>` に対応表による1列単位の属性継承を追加。同じ破片から複数の粉じんへ引き継ぐため、同じsource indexの繰り返しを許容する。欠損はReject／UseDefaultを明示する。存在する列の型／単位不一致を既定値で隠さず失敗し、範囲外indexや容量不足は出力を書き換えない。入力／出力は非重複で、所有は呼び出し側。全列とspawnの一括commit、値の意味に応じた有限性チェック、補間・集約はまだadapter側の設計が必要。型付きspanは借用ビューであり、新規の所有標準コンテナは使用していない。
- `MaterialDust.hpp` に単一破片から複数粉じんを作る独立処理を追加。外部で準備した発生位置・追加速度、明示的な粉じん質量／体積予算、確保済みの子ID範囲を受け取り、色と速度を継承する。親IDを別途保持し、元の破片を消費しない。子ID overflow／親IDとの重複、非有限値、予算の分割underflow、容量不足は出力を書き換えず拒否／Defer。質量・体積は等分の浮動小数点近似であり厳密な総和一致を保証しない。
- この粉じん予算は演出的な追加生成量。物理的な侵食や質量保存を求める場合、破片からの減算と生成を同時に確定する別の変換契約が必要。破断面取得、衝突条件、放出量の評価、グローバルID確保、実ParticleSystemへの投入は未接続。既存破砕コードを変更していない。
- `MaterialTransferTransaction.hpp` に呼び出し側所有CPU配列向けの変換transactionを追加。選択要素・出力容量・台帳容量を事前検証し、確定時だけSpawn追加／source active解除／処理済み記録を更新する。失敗／Deferでは変更せず、同一batch再試行はAlreadyCommittedで二重追加を防ぐ。選択indexと選択IDは厳密昇順、評価は選択要素とbounded台帳のみを走査する。
- このtransactionは単一所有者・相互に非重複なメモリー・途中観測なしを前提に、失敗しない値代入だけで確定する参照実装。OSクラッシュ耐性、並行処理、実solverの確保／GPU投入、任意属性の複数列commitまで保証するものではない。batchキーと要求内容の対応を不変にし、source active／target／台帳を同一checkpointへ復元する必要がある。

- **関連:** `Artifact/include/Layer/ArtifactLayerComponentSystem.ixx`、`Artifact/include/Generator/ArtifactParticleGenerator.ixx`、`docs/planned/MILESTONE_PARTICLE_GEOMETRY_EMISSION_2026-10-10.md`。
- **ユーザーの検討対象:** レイヤーが徐々に煙／粉じんになる表現、通常粒子から砂への変換、破砕からの粉じん放出。Houdini的な組み合わせを既存レイヤーコンポーネントに無理なく収める。当初は記録のみの依頼で、その後「実アプリに影響を与えずコア実装を育てる」方針で独立実装を開始した。実アプリへの接続は行わない。
- **確認できた事実:** Component SystemにはSource／Dynamics／Topology／Emit／RenderExtraction等の評価段階、接触・破砕・粒子生成情報、破片状態と安定IDの型がある。Particleには位置・速度・色・寿命等の固定メンバーと`customData[4]`がある。型の存在だけではソルバー間接続の完成や実行時挙動を保証しない。
- **設計案（未検証）:** レイヤー粒子化では粒子化前のソースを読み、共通の崩壊時刻／フィールドで元画像の消失と粒子の一度きりの放出を同期する。ソルバー間接続は、元を消費する「変換」と元を残す「派生放出」を分け、位置・速度・色・発生時刻・安定IDを引き継ぐ。必要に応じ質量・体積・破断面積・衝突強度を渡す。各ソルバーが状態を所有し、固定刻み境界で受け渡す。UIはComponents専用面の発生元／条件／量／継承設定から始め、ノード表示は後続の選択肢とする。
- **属性設計案（未検証）:** 型付き標準属性（ID・位置・速度・色・質量等）と任意の拡張属性を分ける。属性には所属（粒子／破片／頂点／面／レイヤー等）、型、既定値、座標系・単位、補間・継承・集約規則を定義する。Fieldは位置と時刻から値を評価するもの、属性は要素に保持する値として区別する。要素ごとの文字列辞書は避け、コールドパスでスキーマとハンドルを解決し、実行時は必要な型付き配列を事前確保して参照する。ソルバー固有内部状態まで汎用属性へ置き換えない。
- **価値／懸念:** 共通の接続契約で表現を組み合わせられる。変換は質量・体積の整合、派生放出は発生量の意味と予算を明示する。重複放出、循環接続、座標系不一致、容量超過、GPU／CPU転送、属性欠損、シーク／復元時の結果変化を防ぐ契約が必要。
- **次に確認:** 既存受け渡し経路と属性相当APIの実装を追跡し、再利用範囲を確認する。最初の候補は破砕→粉じんの一方向接続、その後にParticle→Granular変換。保存する設定と再生成可能な状態、checkpoint対象、属性継承とソルバー初期化規則を具体化してから実装範囲を判断する。
