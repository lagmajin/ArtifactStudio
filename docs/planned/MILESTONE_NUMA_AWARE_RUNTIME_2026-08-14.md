# NUMA-Aware Runtime Foundation Milestone

**最終更新:** 2026-08-14
**ステータス:** Not Started

## 目的

デュアルソケットなど複数NUMAノード環境で、大容量の画像・タイル・レンダリング用ワークバッファと処理スレッドを同一NUMAノードへ近づけられる基盤を作る。

通常の単一NUMA環境では既存の挙動と性能を維持し、NUMA APIを利用できない場合も自動的に標準経路へフォールバックする。アプリ全体をNUMA依存にせず、必要な処理だけが任意に利用できる構成とする。

## 非対象

- UIスレッドやQtオブジェクトへのNUMA最適化
- 全スレッドへの強制 affinity
- ReactiveEvents 系への変更
- DiligentEngine／低レベルGPU backend の変更
- NUMA対応を理由にした既存データ構造の大規模な置換

## 実装フェーズ

### NUMA-1: 現状調査と契約定義

- Windowsで取得できるNUMAノード、processor group、論理プロセッサ情報を整理する
- 単一NUMA、デュアルソケット、API利用不可環境の期待挙動を定義する
- OS依存型を公開APIへ漏らさないインターフェースを設計する
- メモリ確保、トポロジー照会、スレッド配置を別責務として分離する

受入条件:

- NUMA非対応環境を単一ノードとして表現できる
- Windows固有型をCoreの公開契約から隠せる

### NUMA-2: Topology abstraction

- NUMAノード一覧と論理プロセッサ所属を取得する薄いラッパーを追加する
- ノード数、現在プロセスの所属、利用可能メモリを照会できるようにする
- processor groupをまたぐ環境でも識別情報を失わない

受入条件:

- 単一ノードでは追加コストが小さい
- API失敗時に安全な単一ノード結果を返す

### NUMA-3: NUMA memory abstraction

- preferred node指定付きの大容量バッファ確保APIを追加する
- 確保失敗時は標準確保へフォールバックする
- 解放経路を確保方法と整合させる
- 必要に応じて `std::pmr::memory_resource` へ接続できる設計にする

受入条件:

- 呼び出し側がWindows APIやノードマスクを直接扱わない
- NUMA指定なしの既存経路を変更しない
- アラインメント、ゼロサイズ、解放、失敗時の挙動が文書化される

### NUMA-4: Execution domain

- ノード単位の処理ドメインを表すAPIを追加する
- current threadへのaffinity適用は明示的な opt-in とする
- processor group制約を内部実装へ閉じ込める
- affinity適用に失敗しても処理自体は継続できるようにする

受入条件:

- 通常のスレッドプールを強制的に固定しない
- affinityを使う処理と使わない処理を同じ呼び出し規約で扱える

### NUMA-5: Render／image work-buffer integration

- 大容量の画像タイル、CPU合成用バッファ、レンダリング用scratchを候補にする
- データ所有ノードと処理タスクの対応を明示できるようにする
- 全体共有データを無理に複製せず、タイル単位の局所性を優先する

受入条件:

- 単一NUMA環境で出力結果と既存経路が一致する
- デュアルソケット環境でlocal／remote memoryの差を測定できる
- NUMA最適化が悪化する処理では容易に無効化できる

### NUMA-6: Diagnostics and acceptance

- NUMAノード数、processor group、選択ノード、フォールバック理由を診断可能にする
- 大容量バッファ処理のlocal／remote access、スループット、レイテンシを記録する
- 単一NUMA、デュアルソケット、NUMA無効化の比較結果を残す

受入条件:

- 最適化の有効／無効を同一条件で比較できる
- 性能向上が確認できない処理には適用しない判断基準がある
- NUMA API失敗時にユーザー操作やレンダリングが停止しない

## 推奨配置

- OS非依存の契約: `ArtifactCore`
- Windows実装: `Artifact` または既存のPlatform実装領域
- 利用先: 大容量画像・タイル・CPUレンダリングワークバッファから開始

## 注意事項

- NUMAはP-core／E-core問題とは別であり、Alder Lake系の単一NUMA環境では既定経路を維持する
- NUMA対応を導入する前に、データ局所性、false sharing、タスク粒度を確認する
- 新しいシグナル／スロット、QtCSS、QImage本流、ReactiveEventsには接続しない
- 実装前に対象ファイルと既存のプラットフォーム抽象化を確認し、モジュール依存を最小化する

## 完了条件

- NUMA検出、メモリ確保、実行ドメインの薄い抽象化が存在する
- 非NUMA環境の既存挙動を維持する
- 少なくとも一つの大容量ワークバッファ経路で利用できる
- デュアルソケットでの測定結果と、無効化時のフォールバック結果が文書化される
