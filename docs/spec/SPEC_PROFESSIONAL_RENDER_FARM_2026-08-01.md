# プロフェッショナルレンダリング基盤 要件定義

**日付**: 2026-08-01
**比較対象**: Thinkbox Deadline, Pixar Tractor, Smedge, HQueue, AFANASY
**現状**: 基本的な Master/Worker + RPC + チェックポイントはあるが、プロダクションで使うには不足多数

---

## 1. 現状あるもの（すでに △～○）

| 機能 | 状態 | 備考 |
|------|------|------|
| フレーム分割・並列レンダリング | ✅ | `splitRange()` + マルチスレッド |
| リトライ（指数バックオフ） | ✅ | `RetryPolicy` + `FailureManifest` |
| チェックポイント復旧 | ✅ | `CheckpointStore` に30フレーム毎保存 |
| RPC通信（TCP JSON-RPC 2.0） | ✅ | `NetworkRPCServer/Client` |
| ワーカー登録・切断検知 | ✅ | ハートビート30秒タイムアウト |
| セッション台帳 | ✅ | `SessionLedger` |
| 進捗報告 | △ | Master→UI はあるが、Worker内訳・推定残時間なし |
| ローカル Worker | ✅ | `RenderFarmWorker` 実行済み |
| リモート Worker | 🔴 | `FarmWorkerMain.cppm` 実質スタブ（レンダリングしない） |
| GPU パス | 🔴 | `useMfr` 条件が `!useGpuBackend` で無効化 |

## 2. プロフェッショナル基盤に必要なもの（全不在）

### 2.1 ジョブ管理

| 機能 | 説明 | Deadline対応 | 優先度 |
|------|------|-------------|--------|
| **ジョブ優先度** | 高優先度ジョブが先にワーカーを占有 | ✅ | P0 |
| **ジョブ依存関係** | 「Job B は Job A 完了後に開始」 | ✅ | P0 |
| **ジョブチャンク** | 1ジョブ内のフレーム範囲を任意分割（連続でなくてもOK） | ✅ | P1 |
| **ジョブプール** | ジョブを論理グループ化（ショット単位など） | ✅ | P2 |
| **ジョブテンプレート** | 出力設定・ワーカー要件をプリセット化 | ✅ | P1 |
| **ジョブ一時停止/再開** | 実行中のジョブを停止し後で続行 | ✅ | P1 |
| **ジョブ複製** | 設定を変えてジョブをコピー | ✅ | P2 |
| **ジョブタイムアウト** | N時間経過で自動失敗（スタック防止） | ✅ | P0 |
| **フレームタイムアウト** | 1フレームがN分以上なら失敗扱い | ✅ | P1 |

### 2.2 ワーカー管理

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **ワーカーケイパビリティ** | GPUベンダー、VRAM、RAM、OS、プラグイン一覧を宣言 | P0 |
| **ジョブ-ワーカーマッチング** | 「このジョブは RTX 4090 必須」などの要件指定 | P0 |
| **ワーカープール** | ワーカーをグループ化（"GPU_Farm", "CPU_Farm"） | P1 |
| **ワーカー状態（詳細）** | Idle/Rendering/Starting/Error/Offline/Maintenance | P1 |
| **ワーカースケジューリング** | ワーカーがアイドルになると自動で次のジョブを割り当て | P0 |
| **ワーカープリエンプション** | 低優先度ジョブを中断して高優先度に割り当て | P2 |
| **ワーカー自動更新** | 新バージョンのワーカーを自動配信 | P3 |
| **ワーカー健全性チェック** | 定期的にベンチマークを実行し劣化検出 | P3 |

### 2.3 ジョブ実行

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **事前チェック** | 出力パス書き込み可能か、必要プラグインがあるか | P0 |
| **検証パス** | まず1フレームだけ試しにレンダリングして成功を確認 | P1 |
| **タイルレンダリング** | 1フレームを分割して複数ワーカーで並列処理（超大解像度向け） | P2 |
| **プログレッシブ出力** | まだ全フレーム完了していなくても完了フレームは即確認可能に | P2 |
| **出力検証** | レンダリング後のフレームをチェック（黒フレーム/破損検出） | P1 |
| **サムネイル生成** | レンダリング中に低解像度プレビューを生成 | P2 |

### 2.4 セキュリティ

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **認証** | ワーカー登録時のパスワード/トークン認証 | P0 |
| **TLS暗号化** | TCP通信をTLSで暗号化（現在は平文JSON） | P1 |
| **認可** | ワーカーごとに実行可能なジョブを制限 | P2 |
| **サンドボックス** | ワーカーがファイルシステムの許可されたパスのみアクセス | P2 |

### 2.5 監視・アラート

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **Webダッシュボード** | ブラウザから全ジョブ・全ワーカーの状態を監視 | P1 |
| **REST API** | 外部ツールからジョブ投入/状態取得 | P1 |
| **メール/Slack通知** | ジョブ完了/失敗時に通知 | P2 |
| **Prometheus/Grafana メトリクス** | ワーカー稼働率、平均レンダリング時間、失敗率 | P3 |
| **ログ集約** | 全ワーカーのログを中央収集 | P2 |
| **カスタムアラート** | 「失敗率 > 10%」「待機ジョブ > 5」でアラート | P3 |

### 2.6 コスト管理

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **使用量トラッキング** | ワーカーごとのレンダリング時間を積算 | P2 |
| **コスト見積もり** | ジョブ投入前に推定所要時間を表示 | P2 |
| **課金** | ユーザー/プロジェクト別にコストを割り当て | P3 |

### 2.7 環境管理

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **環境変数継承** | ワーカーごとに異なる環境変数セット | P2 |
| **プラグインバージョン管理** | ワーカーのプラグイン一覧とバージョンを照合 | P1 |
| **OCIO config 配信** | 全ワーカーに同一の OCIO config を使用させる | P1 |
| **プロジェクトパス解決** | ネットワークパスのマウント/UNCパス解決 | P1 |

### 2.8 出力管理

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **出力バージョニング** | 同名ファイルの上書きを防ぎ v001, v002 等で管理 | P1 |
| **出力先検証** | 出力パスが存在し書き込み可能か事前チェック | P0 |
| **出力フォーマット検証** | 指定コーデック/フォーマットが利用可能か事前チェック | P1 |
| **部分出力からの復旧** | 中断ジョブを再開する際、既存ファイルをスキップ | P0（チェックポイントと連携） |
| **出力ファイル整合性チェック** | 全フレームファイルが存在しサイズ > 0 であることの確認 | P1 |

### 2.9 キュー管理

| 機能 | 説明 | 優先度 |
|------|------|--------|
| **キュー状態永続化** | アプリ再起動後もキュー状態を復元 | P0 |
| **キューインポート/エクスポート** | キュー設定を JSON で保存/読込 | P2 |
| **一括操作** | 複数ジョブの一括停止/再開/削除/優先度変更 | P2 |
| **履歴** | 完了ジョブの履歴を保持し後で再投入可能に | P2 |

## 3. 既存コードの修正が必要な箇所

### 3.1 Master のバグ修正

| 箇所 | 問題 | 修正内容 |
|------|------|----------|
| `executeLocalRange()` L176-182 | `request.renderFrame(frame)` の戻り値を確認せず常に `ok = true` | 戻り値 `bool` を `ok` に代入 |

### 3.2 Master の制限

| 制限 | 説明 |
|------|------|
| シングルジョブのみ | 現在 `busy_` で排他制御。複数ジョブの同時実行不可 |
| メモリ上のキュー | アプリ再起動でキュー消失 |
| リモートレンジの簡易マージ | `assignRemoteSlices()` の `localRange` から `remoteSlices` を除外するロジックが隣接スライスのみ対応 |

### 3.3 RPC プロトコルの制限

| 制限 | 説明 |
|------|------|
| JSON-RPC 2.0 over TCP 平文 | TLS なし。同一ネットワーク想定 |
| 認証なし | パスワード/トークン認証なし |
| シングルリクエスト | バッチリクエストやストリーミング未対応 |
| 大きなデータ転送非対応 | フレームデータを RPC で送れない（本来は不要。ファイル共有で解決） |

## 4. 全体優先順位マップ

```
Phase 1 (P0) ─ 今すぐ必要
├── Worker が実際にレンダリングする ← 最重要
├── ジョブ優先度
├── ジョブ依存関係
├── ジョブ・フレームタイムアウト
├── ワーカーケイパビリティ + ジョブマッチング
├── ワーカースケジューリング（自動割り当て）
├── キュー状態永続化
├── 認証
└── 出力パス/部分出力の整合性

Phase 2 (P1) ─ プロダクション用
├── ジョブチャンク
├── ジョブテンプレート
├── ジョブ一時停止/再開
├── タイルレンダリング
├── 出力検証（黒フレーム検出）
├── Webダッシュボード
├── REST API
├── TLS暗号化
├── プラグインバージョン管理
├── OCIO config 配信
├── プロジェクトパス解決
└── 出力バージョニング

Phase 3 (P2) ─ 大規模スタジオ向け
├── ジョブプール
├── ワーカープリエンプション
├── サムネイル生成
├── メール/Slack通知
├── ログ集約
├── 使用量トラッキング
└── コスト見積もり
```

## 5. アーキテクチャ変更の要否

現在の Master → Worker の直接 RPC モデルは小規模（<10ワーカー）なら十分だが、大規模（50+ワーカー）では **メッセージブローカー（Redis/NATS/0MQ）を使った Pub/Sub モデル**に移行すべき。

```
現状（Direct RPC）:
  Master ──RPC──→ Worker 1
         ──RPC──→ Worker 2
         ──RPC──→ Worker N

推奨（Pub/Sub Broker）:
  Master ──publish──→ Broker
  Worker 1 ──subscribe──→ Broker
  Worker 2 ──subscribe──→ Broker
  Worker N ──subscribe──→ Broker
```

ただし今の規模（~4ワーカー）では現状のままで十分。P2 移行でよい。
